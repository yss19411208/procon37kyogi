## 1ステップの処理順

| ルール | 出典 | 実装 |
|---|---|---|
| 0ステップ目はアクションフェーズのみ | Q1 A6 / 補足 p.2 | `simulator.simulate_day` |
| 最終ステップは反映フェーズのみ | Q1 A6 / 補足 p.2 | 同上 |
| 反映は 燃料消費 → 移動反映 → うどん獲得 → 燃料補給 → 交通量更新 | Q1 A6 / 補足 p.2 | `reflection_phase` |
| 燃料は移動が完了する反映フェーズで消費される | 補足 p.4 の巡回車A / Q2 A48 | `reflection_phase` で判定 |
| 補給は「1.4のタイミングで同じセルにいた場合」 | Q2 A22 | 同上 |
| 一緒に移動する巡回車は消費→補給の順なので減らない | Q2 A48 / 補足 巡回車E | 同上 |
| 1セル後ろを追う巡回車は補給されない | 補足 巡回車F | 同上 |

**注意**: 「燃料が足りるか」を移動の**予約時**に判定してはいけません。
補足資料の巡回車Aは、燃料1でコスト2の移動を予約し、移動中に補給されて3になり、
到着時に2を消費します。予約時に弾く実装だとこの動きが作れず、補給車の価値が大きく落ちます。

## 道路と交通量

| ルール | 出典 | 実装 |
|---|---|---|
| 交通量 = 前日と前々日の全エージェント滞在ステップ数を全チーム分合算 ÷ チーム数 | 要項 p.9 | `simulator.road_status_for_day` |
| 1日目は全て順調、2日目は1日目のみで決まる | 要項 p.9 | 同上 |
| 交通量 < 混雑基準値 → 順調 / 混雑 ≦ 交通量 < 渋滞 → 混雑 / 渋滞 ≦ 交通量 → 渋滞 | 要項 p.9 | 同上 |
| 滞在ステップ数は「移動後」の位置で数える | Q2 A27 | `reflection_phase` の 1.5 |
| 日の最初（0ステップ）は数えず、日の最後は数える | Q2 A27 | `simulate_day` の構造 |
| 道路の状態は日の途中で変わらない、全チーム共通 | 要項 p.9 | 日ごとに1つの dict を共有 |
| 混雑基準値1〜5、渋滞基準値2〜10、正の整数 | Q1 A13 / Q2 A30 | `generator` / `validate_problem` |
| 各セルの交通量そのものは配られない（状態だけ） | Q1 A12 | ビューアでは自分で計算して表示 |

割り算の丸め誤差を避けるため、実装では `合算 ÷ players ≧ 基準値` を
`合算 ≧ 基準値 × players` に置き換えています。整数同士なので完全に同値です。

### 本選の対戦チーム数

付7 によると、1回戦は10ブースに分かれ、**1試合は9〜10チーム同時**です。
各試合の上位5チームが準決勝へ、6位以下が敗者復活戦へ進みます。
準決勝は9チーム、決勝は10チームです。

交通量は「合算 ÷ チーム数」なので、`players` の値は道路の混み方を直接左右します。
このプログラムの自己対戦は4体なので、既定では `players=4` の問題を生成します。
`players` を9や10にすると、4体分の滞在数を9や10で割ることになり、
本番より道路が空いた状態になります。メニューで選べるようにしてあります。

## 公式サーバーとの照合結果

公式配布の簡易版回答用サーバー（2026年8月20日公開）を実際に動かし、
4体のAIで試合を戦って突き合わせました。**ずれは0件です。**

確認したのは次の2点です。

1. 翌日にサーバーが返す自チームの位置と燃料が、こちらの予測と一致するか
   → 移動時間・燃料消費・補給・うどん獲得の判定が公式と同じであることの確認
2. 翌日にサーバーが返す道路状態が、こちらの予測と一致するか
   → 交通量の数え方（滞在ステップ数の全チーム合算 ÷ チーム数）が公式と同じであることの確認

混雑基準値1・渋滞基準値2まで下げた設定でも照合し、サーバーから
順調・混雑・渋滞の3状態すべてが返ってくる状況で一致を確認しています。

この照合は `tests/test_official_server.py` に入っています。
`server/` に公式バイナリを置くと自動で走り、置いていなければスキップされます。
メニューの「7. 公式サーバーと照合する」からも実行できます。

## 回答システムのAPI

出典: 回答システムに関する情報（redoc-static.html の OpenAPI 定義）

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/setting` | 試合設定（マップ構成）。`startsAt` は確定するまで 0 |
| POST | `/agent` | エージェント種別の配列（例 `[0, 1, 0, 1]`） |
| GET | `/` | 各日開始時点の状態（自チーム・他チーム・道路状態） |
| POST | `/` | その日の行動計画。戻り値の `revision` が0以上なら受理 |

認証はトークンです。ヘッダー `Procon-Token` かクエリ `token` のどちらでも通ります。
HTTP/1.1 のみ対応、リクエストは秒間5回程度が目安です（質問回答集その2 A41 / A42）。
実装は `hexa/client.py` にあります。

### 試合設定JSON（簡易版サーバーに渡すもの）

`{"problem": {...}, "teams": [{"token": "...", "name": "..."}]}` という形です。
`players` は書きません。`teams` の要素数がそのまま参加チーム数になります。
組み立ては `hexa/localserver.build_config` にあります。
