# 最終点検レポート

10,000,000エピソードの長時間学習と本選投入に向けて、
「その規模でだけ壊れる箇所」を中心に点検しました。

---

## 1. 見つけて直した重大な不具合（2件）

### ★ ラウンドごとに同じ問題を解き直していた

おまかせ学習（メニュー2a）は学習を小分けにして回しますが、
**毎回まったく同じ乱数の種を使っていました。**

つまり1,000万エピソード回しても、実際に経験するのは最初の1ラウンドぶん
（2,000問）だけで、それを5,000回解き直すだけになっていました。
長時間学習の意味が丸ごと失われる不具合です。

ラウンド番号を種に混ぜて、毎回違う問題列になるようにしました。
回帰テスト `test_rounds_do_not_repeat_the_same_problems` で固定しています。

### ★ 探索率と学習率が毎ラウンド最初に戻っていた

同じく小分けの影響で、探索率（0.35→0.03）と学習率（0.08→0.01）が
**1ラウンドごとにリセット**されていました。
いつまでも探索が強いまま、学習率も下がらないので、収束しません。

学習全体の中での位置を渡すようにして、1,000万回を通して
少しずつ下がるようにしました。回帰テスト
`test_progress_spans_the_whole_run_not_one_round` で固定しています。

---

### ★ 検証が小さいマップしか見ていなかった

学習では大きさも型も振っていましたが、**検証は 8×8 と 12×12 の2種類しか
測っていませんでした。** 20×20 と 32×32 は一度も測られません。

その結果、「伸びたか」「どの型が苦手か」「AIを大きくするか」という
3つの判断がすべて小さいマップだけで決まり、大きいマップで弱くなっていても
気づけない状態でした。

既定を4サイズ（8×8 / 12×12 / 20×20 / 32×32 × 5型 = 20問）に変え、
メニュー2aで細かさを選べるようにしました。4未満を選ぶと警告が出ます。
回帰テスト `ValidationCoverageTest` で固定しています。

---

### ★ AIがマップの大きさと地形を区別できていなかった

判断の材料がすべて「マップ基準の割合」に正規化されていたため、
**8×8 と 32×32 が同じに見えていました。** 地形の構成も、燃料の厳しさも、
渋滞のなりやすさも、盤面からは分かりません。

学習ではいろいろなマップを経験していましたが、区別がつかない以上、
できあがるのは全部を平均した1つの戦い方だけです。
「大きいマップではこう」「山地だらけなら燃料を優先する」という
場面ごとの使い分けは、原理的に学習できませんでした。

その問題そのものを表す材料を9個追加しました（広さ・縦横の偏り・
池/道路/山地の割合・燃料の余裕・渋滞のなりやすさ・店の多さ・系列の細かさ）。
掛け算の対象にも入れてあるので、cross や large では
「マップが広い かつ 店が遠い なら」のような条件付きの判断が書けます。

巡回車の材料は23→32個、補給車は13→18個になりました。
回帰テスト `MapAwarenessTest` で、8×8 と 32×32 が区別できること、
地形・燃料・渋滞の違いが見えることを固定しています。

### ★ 64並列で学習するとメモリ不足でプロセスごと殺された

経路表のキャッシュを「表の個数」（4096個）で制限していました。
1つの表の大きさはマップのセル数に比例するので、32×32 では1つ150KBあり、
**1プロセスで610MB、64並列で38GB** に達します。搭載32GBでは足りず、
OOM Killer に強制終了されました（実際に発生）。

セル数の合計で制限するように変えました（20万セルまで）。

| マップ | 直す前 | 直した後 |
|---|---|---|
| 8×8 | 3,125表 | 3,125表 / 0.8MB |
| 20×20 | 4,096表 | 500表 / 3.5MB |
| 32×32 | 4,096表 = 610MB | **195表 / 7.1MB** |

64並列での合計は **38GB → 0.4GB**。速度の代償は32×32の1試合で
17.4秒→18.5秒（約6%）でした。

あわせて、子プロセスを作る前に `gc.freeze()` を呼ぶようにしました。
これがないと子プロセス側のガベージコレクションが親から引き継いだメモリに
触れてコピーが発生し、並列数のぶんだけメモリを食います。

メニューの「経験に使ってよいメモリ」も、親プロセス1つぶんであることを
明記し、既定を「登録したメモリ ÷ 4」に変えました。プロセス数を入れたあとに
おおよその使用量も表示します。

### ★ 決勝でタイプ選択が制限時間に間に合わなかった

本選の条件で測ったところ、決勝（32×32・7体）のタイプ選択に **124.1秒**
かかりました。制限は120秒です。間に合わないと種別を提出できず、
全エージェントが巡回車になります（フォーマット資料 p.3 / 質問回答集その2 A53）。
補給車を一切使えない状態で決勝を戦うことになっていました。

時間制限を入れ、試す順番も変えました。

1. まず貪欲な方策で「補給車0台〜最大」を一通り試す（台数の決定に直結）
2. 残り時間があれば、学習したAIで同じ台数を試して上書きする

締切が近づいたらその時点の最良を返します。全部試し切れなくても、
**台数の候補は必ず一周しています。**

| | 実測 | 制限 |
|---|---|---|
| 1回戦 16×16 | 1.9秒 | 60秒 |
| 準決勝 24×24 | 7.1秒 | 90秒 |
| 決勝 32×32（参考マップ） | 28.6秒 | 120秒 |
| 決勝 32×32（10日の重い想定） | 81.5秒（54/77通り） | 120秒 |

### ★ 検証が本選と別のゲームで行われていた

本選の系列数は、スポット数に対してとても多い設定です。

| | スポット | 系列 | 1系列あたりの店 |
|---|---|---|---|
| 本選1回戦 | 16 | 10〜14 | 1.1〜1.6店 |
| 本選決勝 | 32 | 20〜28 | 1.1〜1.6店 |
| 以前の検証(max) | 32 | 10 | 3.2店 |

**ほとんどの系列が1店しかありません。** 取り逃したらその系列は二度と
取れない勝負で、第1優先の種類数がほぼすべてを決めます。
以前の検証は1系列3店前後で、取り逃してもリカバリが効く別のゲームでした。

検証を本選の3条件そのものに変えました（1回戦16×16/4体/16店/系列10-14、
準決勝24×24/5体/24店/系列14-20、決勝32×32/7体/32店/系列20-28）。
学習側も、ランダムに振る回の半分を本選と同じ条件にしています。

### ★ 型ごとの燃料と基準値が一度も効いていなかった

マップの型（街・山岳・群島・平原）に燃料と混雑/渋滞基準値の範囲を
持たせていましたが、**生成側がその指定を無視していました。**
どの型でも燃料1〜3倍・混雑1〜5・渋滞2〜10のままで、地形の割合だけが
変わっていた状態です。編集が適用されていなかったことに気づかず、
そのまま残っていました。

直した結果、型ごとにはっきり分かれるようになりました。

| 型 | 燃料 | 混雑 | 渋滞 |
|---|---|---|---|
| 山岳 | 1.08〜1.75倍 | 2〜5 | 4〜9 |
| 平原 | 1.61〜2.74倍 | 3〜5 | 6〜10 |
| 本選 | 1.20〜1.90倍 | 1〜2 | 3〜5 |

あわせて、各日のステップ数も型ごとに調整できるようにしました。
参考マップは W+H の1.0〜1.5倍と、許される範囲（1〜4倍）の下限寄りでした。
以前は1〜4倍の一様分布だったので、本選より2倍以上ゆとりのある試合で
学習していたことになります。

### ★ 地形がばらばらに置かれていた

参考マップは地形が**かたまって**います。sample_32 では道路の出現率が24%なのに、
隣が道路である割合は36%。山地も31%に対し37%でした。

以前の生成器は完全なランダム散布（出現率と隣接率がほぼ同じ）だったので、
**道路が1マスずつ孤立していました。** 道路は移動1ステップと速いのに、
つながっていなければ一度も連続して使えません。本選とは別のゲームで
学習していたことになります。

種を蒔いて広げる方式に変え、かたまり具合も型ごとに振るようにしました。
街は道路が長くつながり、山岳は山脈になり、群島は島と水路になります。
回帰テスト `TerrainStructureTest` で、道路の半分以上が他の道路と
隣接していることを固定しています。

### ★ players と実際のチーム数がずれていた

メニュー3で players=4 を選んでも、AIが10体いれば10チームで戦っていました。
交通量は「全チームの滞在数 ÷ players」で計算されるので、
**10チーム分の滞在数を4で割る**ことになり、道路の混み方が本番とまったく
違うものになっていました。

players に合わせてチーム数を絞るようにしました。ずれる場合は画面に
理由も表示します。

### ★ 燃料切れの巡回車が、その日ずっと復帰できなかった

実戦で「7体中2体が5日間ずっと止まったまま、在庫は60以上残っている」
という状態を確認しました。原因は2つ。

行ける店が1つもないとき（＝たいてい燃料切れ）、**その日の残り全部を
待機に決めていました。** 途中で補給車が来て満タンになっても、
計画が固定済みなので動き出せません。こまめに選び直すようにしました。

もう1つは、補給車が立ち往生した巡回車を最優先にしていなかったこと。
燃料0の巡回車は補給されるまで0玉のままなので、そこへ行くことを
最優先にしました。どの立ち往生車へ行くかは引き続き学習が決めます。

結果: 同じ問題で玉数 253 → 273。

### ★ 作戦が増えるほど1回の判断が重くなっていた

学習で作戦が増えると（最大48個）、毎回全部を試すため
1判断が5ミリ秒→20ミリ秒に膨らんでいました。実戦で1日の候補が
数千件から20件まで落ちていた原因がこれです。

1回の判断で試す数を12個に固定しました。出発点の8つ＋成績の良かった
ものを選びます。**手持ちからは何も消しません。**

### ★ 経路探索が遅く、事前試走が足りなかった

プロファイルすると処理時間の**89%がダイクストラ法**でした。
探索状態を辞書からリストに置き換え（セル番号は連番なのでリストで引ける）、
1試走 2.40秒 → 0.60秒に。

さらに `_jammed_status`（全道路が渋滞した状態）を判断のたびに作り直し、
`terrain_at` を400万回呼んでいました。問題ごとに1回だけ作るようにして、
AI方策の1試走 2.75秒 → 1.96秒。

候補の店すべてで経路を歩き直していた処理も上位5件に絞りました。

事前試走の回数（AI32体・10日の重い想定）:

| | 直す前 | 直した後 |
|---|---|---|
| 1回戦 16×16 | 139通り | 202通り |
| 準決勝 24×24 | 62通り | 97通り |
| 決勝 32×32 | 34通り | 51通り |

### ★ 巡回車どうしが「先着優先」で担当を決めていた

エージェントは番号の若い順に目標を決め、他が予約した店を避けるだけでした。
つまり次のような無駄が残っていました。

    0番が店Aを予約したが、実は1番のほうがAに近く、
    0番は店Bのほうが近かった。入れ替えれば両方が得をする。

番号が若いというだけの理由で0番がAを取っていたということです。
各日の開始時に全ペアを試し、移動歩数の合計が減るなら交換するようにしました。
判定は公式の優先順位どおりで、**種類数と日別累計を落とす交換は採用しません。**

実測（未見6問の玉数と日別累計）:

| | 日別累計 | 玉数 |
|---|---|---|
| 入れ替えなし | 78.83 | 220.5 |
| **入れ替えあり** | **79.33** | **228.2（+3.5%）** |

**どちらの優先順位も同時に改善しました。**

### 道すじの枝分かれ探索は効果がなく、既定では切ってあります

「1本ずつ貪欲に伸ばすのをやめ、数本を並行して伸ばせば良い順番が見つかる」
と考えて実装しましたが、実測では逆効果でした。

| | 玉数 |
|---|---|
| 枝1本（採用） | 228.2 |
| 枝3本 | 219.3 |

枝を選ぶ基準が「作戦の評価値の合計」であって玉数そのものではないためだと
見ています。評価値の良い順番が玉数の多い順番とは限りません。
仕組みは `BEAM_WIDTH` として残してあります。

### 「今日はどれだけ長い日か」を材料に追加

これまでは「残りステップに対する割合」しか見ておらず、
**32歩の日と246歩の日を絶対値で区別できませんでした。**
短い日は近場を確実に、長い日は遠征、という使い分けに必要です。

材料29番（今日の長さ）と30番（今日のうちどれだけ使ったか）を追加。
素の材料は38個から40個になりました（simple 40 / cross 211 / large 781）。

### 補給車どうしの担当の入れ替え

巡回車と同じく、補給車も番号の若い順に担当を決めていました。
合流までの歩数の合計が減るなら交換するようにしています。
**燃料が尽きている巡回車の到着が遅くなる交換は採用しません。**

ただし**効果は限定的です。** 補給車が2台以上の試合でしか働かず、
多くの試合は1台だからです。12問での実測では差が出ませんでした
（6問では+1.6%）。害はないので残してあります。

### 学習時間の短縮は、ほとんど稼げませんでした

1エピソードの時間は大きさで大きく違います（5チーム・1コアの実測）。

| | 1エピソード |
|---|---|
| 1回戦 16×16 | 0.7秒 |
| 準決勝 24×24 | 2.0秒 |
| 決勝 32×32 | **8.0秒** |

小さいほうを多めに引けば時間を稼げますが、**実戦で一番弱いのが32×32**
（1位の63〜78%）なので、減らしすぎると弱点がそのまま残ります。
40:30:30 にして平均3.57秒→3.28秒、**1.09倍**にとどめました。
100万回で16.5時間→15.2時間です。

大きな短縮は、すでに済ませた経路探索の高速化（1試走2.40秒→0.60秒）と
渋滞状態のキャッシュ（AI方策2.75秒→1.96秒）で取ってあります。
ここから先は、覆う範囲を削らないと稼げません。

### 待機を学習に任せる仕組み ── 実測が否定したので既定は無効

「燃料を温存して明日に回す」判断を学習に任せられるようにしましたが、
**実測では必ず日別累計が下がりました**（未見12問）。

| | 日別累計 | 玉数 |
|---|---|---|
| **待機なし（採用）** | **76.50** | 234.8 |
| 待機あり 2割まで | 75.83 | 239.8 |
| 待機あり 4割まで | 75.42 | 238.8 |

「今日まだ取っていない系列が1店でも残っているなら待たせない」という
歯止めを3段階で強めましたが、それでも 75.58 までしか戻りませんでした。
待った巡回車のぶん、その日に回れる店が減るためだと見ています。

**日別累計は公式の第2優先で玉数より上です。** 実戦で1位を取った2試合は
どちらも日別累計で勝っているので、玉数が+2%増えても採用しません。

`TOURING_WAIT_BUDGET = 0.0` で無効にし、仕組みは残してあります。
学習後に試すときは 0.2〜0.4 にしてください。そのときは玉数だけでなく
**日別累計も必ず確認**してください。

回帰テストで「既定が0であること」「待機を許しても一日じゅう動かない
巡回車が出ないこと」「系列が残っているうちは待たせないこと」を固定しています。

### ★★ 学習が構造的に破綻していた（最重要）

60万エピソード回したログを見て見つけました。2万回目から最後まで
ほぼ毎ラウンド「重みが壊れたAIがいます」が出続け、そのたびに
最良へ巻き戻されていました。**61時間かけて一歩も進んでいません。**

原因は更新式です。

    重み += 学習率 × 誤差 × 材料

この形が安定するのは `学習率 < 2 ÷ |材料|²` のときだけです。
材料が増えるほど上限が下がるのに、学習率は0.08で固定でした。

| | 材料 | \|材料\|² | 安全な上限 | 0.08 は |
|---|---|---|---|---|
| simple | 40個 | 15.2 | 0.132 | 安全 |
| cross | 211個 | 30.2 | 0.066 | 危険 |
| large | 781個 | 121.5 | **0.017** | **5倍の危険** |

`simple` だけが偶然安全圏でした。実測では **large はわずか3エピソードで
破綻**し、重みが 3.85×10¹¹⁷ まで飛びました。

更新のとき `|材料|²` で割るようにしました（正規化）。材料が何個でも
一歩の大きさが揃うので、学習率は「誤差のどれだけを一度に埋めるか」の
意味になり、1未満なら必ず収束します。

| | 修正前 | 修正後 |
|---|---|---|
| simple | 正常 | 正常（最大2.23） |
| cross | 危険 | 正常（最大1.77） |
| large | **3回目で破綻** | **正常（最大0.44）** |

「安定させたぶん学習しなくなった」わけではないことも確認済みです。
同じ材料を200回学習させて誤差が8割以上減ることを
`WeightStabilityTest` で固定しています。

### ★★ 送れなかった案を採用したことにしていた（予測のずれの原因）

実戦で毎試合3〜5件の「ずれを検出」が出ていました。

    予測[128, 240, 48, 182] / 実際[128, 0, 240, 48]

原因は、提出に失敗しても `best` を進めて、それを予測に使っていたことです。
サーバーが持っているのは**最後に受理された回答**なので、
送れなかった案を採用したことにすると、予測と実際がずれます。

**受理された案だけを予測に使う**ようにしました。提出が失敗したら
その候補は捨てて次を試します。メニュー7の照合（位置と燃料360回）は
もともと一致していたので、シミュレータではなく production 側の問題でした。

### ★ 本番モードが落ちない保証

本選で止まったら0点です。メモリ不足でも想定外の失敗でも、
提出だけは続ける形にしました。

- 候補づくりで `MemoryError` → 貯めた候補を捨てて探索を打ち切る（提出済みは残る）
- 候補づくりで想定外の失敗 → その候補を捨てて次へ進む
- 状態が取れない → 全員待機を送って次の日へ進む

### 池と山地を実マップ並みにかためた

練習場の実マップを測ると、池の超過分が **+0.63**、山地が **+0.52**、
道路が +0.28 でした。以前の生成器は池 +0.26 どまりで、ばらけすぎです。

池は clump の1.6倍、山地は1.3倍でかためるようにし、型ごとの上限も
引き上げました。18マップで池が最大 +0.59、山地が最大 +0.57 まで出ます。
連結が壊れるものは1マスずつ採用判定で弾いているので、分断は起きません。

### 9チーム戦への対応

本選の初戦は津山高専＋8チームで9チーム戦です。交通量は
「全チームの滞在数 ÷ players」なので、players が変われば道路の混み方も
変わります。学習で9チームと10チームを半々で出すようにしました。

### 訪問順の並べ替え

作戦は「次に一番良い店」を継ぎ足して道すじを作ります。1店ずつ見ると
最善でも、**並び全体としては遠回りになる**ことがあります。

実戦の9日ぶんを調べると、実際に回った順番の合計2574歩のうち
**249歩（9%）が並べ替えだけで削れました。** 1日目の車1は110歩が64歩まで縮みます。

隣り合う2店を入れ替える操作を、改善が止まるまで繰り返します。
歩数と燃料が足りない並びは採用しません。

| | 種類 | 日別累計 | 玉数 |
|---|---|---|---|
| 並べ替えなし | 15.80 | 77.90 | 246.3 |
| **並べ替えあり** | 15.80 | 77.90 | **251.0（+1.9%）** |

**順番を変えるだけなので、取れる系列も玉数も減りません。**
日別累計を落とす心配がないのが、この方法の良いところです。

先読みの長さも測り直しましたが、3店のままが最適でした（4店で247.0に低下）。

### 歩数は余っていませんでした（前回の報告の訂正）

「1日の予算の3〜7割が余っている」と報告しましたが、**私の計測ミス**でした。
「動いた手の数」を歩数と取り違えていました。山地1歩は4ステップ消費します。

正しく測ると**91〜100%使い切っています。**

本当の問題は「1玉あたりに使う歩数」でした。

| 1日の歩数 | 獲得 | 1玉あたり |
|---|---|---|
| 57歩 | 28玉 | 8.1歩 |
| 63歩 | 17玉 | 14.8歩 |
| 177歩 | 34玉 | 20.8歩 |

ほぼ同じ歩数でも1.6倍の差が出ます。長い日ほど効率が落ちるのは、
取り尽くした店を避けて遠くへ行くためです。

### 日別累計 ── 候補を増やす形で改善

日別累計は公式の第2優先で、玉数より上です。実戦で1位を取った試合は
どちらも日別累計で勝っていました。

**失敗した方法**: すべての判断で「今日まだ取っていない系列」を優先させる。
日別累計まで下がりました（77.90→73.00 / 玉251.0→185.3）。遠い店へ
無理に向かうと、近場を回れば取れたはずの別の系列を落とすためです。

**採用した方法**: 系列優先の方策を**候補の1つとして加えるだけ**にする。
最終的な選択は公式の優先順位で行うので、この方策が勝つのは
「本当に日別累計が増えるとき」だけです。候補が増えるだけなので、
悪くなることは構造的にありません。

| | 日別累計 | 玉数 |
|---|---|---|
| 系列優先なし | 67.10 | 145.5 |
| **系列優先あり** | **68.10** | 139.9 |

玉数は下がりますが、**日別累計は玉数より上の指標**なので採用です。

### 並列を流し続ける形に

以前は「子の数だけ作って全員終わるまで待つ」形でした。1エピソードは
16×16で1.7秒、32×32で19.1秒と11倍違うので、20並列でも1つ遅いものが
全体を縛り、実効33%まで落ちます（CPU使用率43.9%として実測）。

常に `子の数×2` 件を流しておき、終わった順に取り込む形に変えました。
30エピソードで正常完走を確認しています。

**効果の実測は64コア環境で確認してください。** 学習開始後に
`top -bn1 | head -5` を見て、CPU使用率が43.9%から上がっていれば成功です。

### リアルタイム監視（メニュー18）

メニュー8や15で戦っているあいだ、盤面・探索の様子・提出した行動・
日ごとの詳細を1秒ごとに見られます。

**本番の処理とは完全に別です。** 本番側は軽いJSONを1つ書くだけで、
実測0.4ミリ秒。ビューアを開いても閉じても落ちても、試合に影響しません。
書き込みに失敗しても試合は止まりません。

### ★ ビューアが必要とする項目を送っていなかった

実戦で「ビューアの右側が壊れる」「マップが壊れる」という不具合が出ました。

原因は、本番モードが `refuels` に**件数（整数）だけ**を渡していて、
ビューアが読む `refuelEvents` が存在しなかったこと。燃料ゲージも
できごと欄もそこを読むので崩れます。さらに `daySteps`
`startPositions` `startFuels` も送っていませんでした。盤面の再生は
この3つが土台なので、マップの描画も壊れます。

見本では自分で全項目を詰めていたため気づけませんでした。
**本番の経路を通していなかった**のが原因です。

4項目を送るようにし、`refuels` は1件ずつの記録に変えました。
実際に本番と同じ流れを5日ぶん通して不備ゼロを確認し、
`MonitorPayloadTest` 5件で固定しています。

### 探索中も盤面が動くようにした

いままで盤面が動くのは1日1回、提出後だけでした。探索中の60秒は
止まったままです。**暫定の最良案を盤面に出す**ようにしたので、
より良い案が見つかるたびに動きと軌跡が差し替わります。
軌跡の作り直しは1.5秒に1回までに制限しています。

### 1日に作れる候補を4割増やした

実戦の24x24・10日で、候補が115〜432件しか作れていませんでした
（16x16では1500件前後）。1案に80ミリ秒かかっていたためです。

プロファイルで3つの無駄が見つかりました。

| | 内容 |
|---|---|
| 採点 | tuple/zip/sum を使い、1案あたり18万回呼ばれていた |
| 店の走査 | 在庫のない店も毎回調べていた |
| 道路のキー | 毎回ソートし直していた（1案あたり8万回） |

1案 80ms → 57〜65ms。55秒で **654案 → 842〜957案**。

**答えは1つも変わっていません。** 未見10問で
種類13.90 / 日別68.10 / 玉139.9 と、高速化の前後で完全に一致しました。
採点式が元の式と一致することもテストで固定しています。

### 候補数は玉数の原因ではありませんでした

32x32の実戦で候補が89〜104件しか作れておらず、これが玉数不足の
原因だと考えて高速化を進めました。**実測がそれを否定しました。**

32x32・235歩の日で、案を増やしたときの最良（同じ問題・同じ条件）:

| 案の数 | 結果 | 経過 |
|---|---|---|
| 25案 | 種類23 / 日別23 / 玉104 | 6秒 |
| 100案 | 種類23 / 日別23 / **玉104** | 23秒 |
| 400案 | 種類23 / 日別23 / **玉104** | 95秒 |

**25案で頭打ちです。** 16倍に増やしても1玉も変わりません。
いまの方策の集まりが出せる最良に、すぐ到達してしまうということです。

残る差は「候補をたくさん作ること」では埋まりません。
**方策そのものの質**＝学習の領域です。

### それでも入れた高速化

無駄な計算は減らしました。答えは1つも変わりません。

| | 内容 |
|---|---|
| 採点 | tuple/zip/sum をやめ、8項目を直接書き下した（1案18万回） |
| 店の走査 | 在庫のない店を毎回調べていたのをやめた |
| 道路のキー | 毎回ソートし直していたのをキャッシュ（1案8万回） |
| マスのコスト | 地形と道路状態から先に表にした（1案60万回） |

未見10問での結果は 種類13.90 / 日別68.10 / 玉139.9 と、

### 燃料を考える経路は、やはり有効でした

重みの段階を5→3に減らす案も、案は増えるのに結果が落ちたので

### ★ 日別累計の取りこぼし ── 原因は燃料の使い切りでした

練習場9試合のうち**5試合で日別累計を落として**いました。
最悪の試合839は、1位が52点満点のところ私たちは42点です。

再現して調べると、**3日目の開始時点で燃料が [96, 11, 6, 0]**。
3台中2台がほぼ空でした。そこから**3304案を試しても12系列止まり**。
当日の探索では絶対に解決できない状態です。

原因は、1日ずつ「種類→日別→玉」で最良を選んでいたこと。今日の点数
だけを見るので明日の燃料が残りません。終了時の燃料は同点のときしか
効かず、歯止めになっていませんでした。

評価の3番目に「明日動けない巡回車の少なさ」を入れました。
**日別累計（2番目）より下、玉数（4番目）より上**です。今日の系列を
1つ落としてまで燃料を残すことはせず、玉数を少し削ってでも明日の系列は
守る、という順番にしてあります。

ただし**燃料に余裕がある試合でだけ**効かせます。9試合で測ると、
余裕のない試合では玉を落とすだけでした。

| 試合 | 燃料の余裕 | 先読みなし | 先読みあり |
|---|---|---|---|
| 839 | 1.16倍 | 日別51 / 玉75 | **日別52 / 玉78** |
| 836 | 0.15倍 | 日別189 / 玉782 | 日別189 / **玉647** |

余裕がない試合では、どのみち燃料は足りません。残そうとすると今日の玉を
捨てるだけで、明日も結局動けません。余裕があるときだけ
「使いすぎないようにする」のが正しい形でした。

9試合の合計:

| | 日別累計 | 玉数 |
|---|---|---|
| 先読みなし | 1098 | 2955 |
| 常に先読み | 1099 | 2795 |
| **余裕があるときだけ** | **1099** | **2958** |

**両方が改善しました。**

### ★ 監視が途中で止まる ── 1回の失敗で永久に諦めていた

原因は、書き込みに**1回でも失敗すると `enabled` を False にして
二度と再開しなかった**ことです。Windows では、ブラウザやウイルス対策が
ファイルを開いている一瞬に `os.replace` が失敗することがあります。

3回まで即座に再試行し、**20回続けて失敗したときだけ**諦めるように

### 位置の先読みは効きませんでした

実装をしました。

**9試合すべてで結果が1点も変わりませんでした。**

理由は、計画がすでに店の近くで1日を終えているからです。最後に訪れるのが
店なので、終了位置は自然と店の上か隣になります。計算を増やすだけなので
`POSITION_REACH_RATIO = 0.0` で無効にし、コードは理由とともに残しました。

### 渋滞の調査 ── 物理的な制約でした

試合927（32×32・混雑基準1・渋滞基準3）を詳しく調べました。

**自分がよく通った道は94〜100%の確率で翌日渋滞します。**
通らなかった道は2〜20%。全チームが同じ良い道に集中するためです。

| | 玉数 |
|---|---|
| 自分だけで走ったとき（渋滞なし） | 549 |
| 実際の渋滞下 | 470 |
| 1位 | 559 |

対策を4つ試しましたが、**いずれも改善しませんでした。**

- 明日の渋滞予測を経路のコストに織り込む → 変化なし
- 予測0.5以上を混雑扱い / 0.8以上を渋滞扱い → 変化なし
- 探索を60案・200案に増やす → 470→478 で頭打ち
- 在庫の多い店への配分を増やす → **470→457 と悪化**

理由は、**その日の渋滞はサーバーから取得済み**で、経路探索がすでに
正しく織り込んでいるからです（渋滞時は道路の利用率が68%→26%に落ちる）。
渋滞日は店までの歩数が中央値118歩になり、1日229歩では2店しか回れません。
**避ける巧さの問題ではなく、物理的な制約**でした。

### ★ 練習場の行動記録（メニュー15のみ）

「なぜその判断をしたか」をあとから追えるよう、練習場の試合を
`logs/match_<ID>.json` に記録します。**本番モードでは記録しません**
（1日60秒しかないため）。試合中は配列に貯めるだけで、
終わってから1回だけ書き出すので探索の速度に影響しません。

| 記録する内容 | |
|---|---|
| 事前試走 | 試した通り数・所要秒・最良の構成とスコア |
| 各日 | 採用案・候補数・出し直し・所要秒・候補の上位5件 |
| 動き | 1歩ごとの位置・燃料・補給イベント |
| **取れなかった店** | **理由つき**（届いた／歩数不足／燃料不足／在庫切れ） |

「届いたのに行かなかった」が多ければ判断の問題、「燃料不足」が多ければ
補給の問題、と切り分けられます。

### 補給の優先順位を「これから足りなくなる車」に

以前は「いま燃料が最も減っている車」を優先していました。実戦958で
調べると、山地に囲まれた店へ片道31燃料かかり、上限46では往復できません
（62必要）。補給が要るのは**いま減っている車ではなく、これから
足りなくなる車**です。向かう先に燃料が届くかを最優先にしました。

### 試合958の分析 ── 1位も満点ではありませんでした

日別53（1位62・満点65）と大きく負けた試合を詳しく調べました。

- 系列12の店は山地に囲まれ、**4台中1台しか燃料が届きません**
- 往復には燃料62が必要で、上限46では不可能
- **1500案試しても13系列そろう計画は0件**
- 1位の62点も満点ではなく、5日で3系列ぶん落としている

つまり**物理的に取り切れない試合**でした。私たちの59との差は3点で、
4日目が9系列に落ちたことが主因です（他の日は12系列）。

36試合248日分と、追加19試合133日分を集計しました。

### ★ 事前試走を複数のコアで走らせます

**事前試走だけ並列にしました。** 1日の計画づくりは「25案を超えると
結果が変わらない」と実測済みなので、並列にしても同じ結果になります。
一方この試走は補給車の台数を決める1回限りの判断で、決勝では
**231通りのうち38通りしか試せて**いませんでした。台数を外すと全日に響きます。

Windows は fork が使えず spawn なので、次の形にしています。

- 問題と重みは**ファイル経由**で渡す（JSONにできる形だけ送る）
- 1つの子に**4つの組み合わせをまとめて**渡し、起動の回数を減らす
- 使うのは**コア数の半分まで**（本番用PCの余力を残す）
- 持ち時間の**55%だけ**並列に使い、残りは1プロセスの探索に回す
- **失敗したら黙って1プロセスに落ちる**（本番を止めない）

実測（2プロセス・25秒）: 並列で16通り＋単体70通り＝**86通り**。
1プロセスのみなら40通り前後なので、倍以上に増えています。

### ★ 「1日の上限」の数え方が誤っていました

ビューアで「100%なのに在庫が残る」と報告をいただき、調べました。

以前は上限を「各店の在庫 × 巡回車の数」で数えていましたが、これは
**全店を全台が回れる前提**です。実戦のログでは「上限33 / 獲得14」と
出ていましたが、1台は1日に**5〜6店しか回れて**いませんでした。

正しくは次の小さいほうです。

- 在庫の都合: 各店の在庫と巡回車の数の小さいほう（1台1日1玉まで）
- **時間の都合: 1台が1日に回れる店の数 × 台数**

店どうしの距離の中央値から回れる数を見積もる形にしました。
記録には `capacity`（実際に取りうる上限）と `stockCapacity`
（在庫だけで数えた理論値）の両方を残します。

**この数字は計画づくりには使っていないので、成績には影響しません。**
記録と分析のための値です。テストで「計画側が使っていないこと」も
固定しました。

ビューアの在庫表示そのものは正しく動いていました。

### 並列を論理プロセッサ数-1に

以前は「コア数の半分」でしたが、本番用PCは試合中これ以外にすることが
ないので、**1つだけ本体用に空けて残り全部**を使います。

あわせて、並列が使えなかったときに**理由を出す**ようにしました。

  - 1コアのとき: 「このPCは1コアなので使いません」
  - 時間が足りないとき: 「残り○秒では足りないので使いません」
  - 子プロセスが失敗したとき: その例外の内容

実戦で「並列で○通り」が出なかったので、次からは原因が分かります。

### ★ 並列が一度も動いていませんでした

試走で時間をほぼ使い切って**いました。順番が逆だったのです。

### ★ 並列を締切まで使い切る

3つ直しました。

**仕事を流し続ける。** 以前は全部をいっぺんに投げて先頭から順に
待っていたため、手の空いた子が遊んでいました。終わった子から次を渡す
形にしています。

**組み合わせを増やす。** 240通りでは足りず、子が仕事待ちになっていました。
4000通り用意します。締切で打ち切られるので余らせても害はありません。

**子プロセスを先に起こす。** Windows は spawn なので、最初の起動に
数秒かかります。試合が始まる前に空の仕事を投げて起こしておけば、
事前試走の持ち時間をまるごと探索に使えます。

並列に使う時間も持ち時間の40%から**80%**に広げました。親は並列の結果を
待たずに自分の試走を進めるので、長く取っても無駄になりません。

プロセス数は**論理プロセッサ数-1**です。1つは通信と監視のために空けます。
12プロセッサなら11本が動き、親を含めて12本が見えます。

### 作戦をその場で改良する仕組み ── 実測で伸びず

「学習済みの作戦をそのまま使うのではなく、その試合に合わせて少しずつ
良くしていけば勝てるのでは」と考えて実装しました（`hexa/refine.py`）。

## 3. 点検して問題がなかったもの

### 公式ルールとの一致

- 公式の簡易版サーバーを起動して**10チーム同時対戦**を実施。
  **予測と実際のズレ 0 件、エラー 0 件。**
  位置・燃料・道路状態のすべてが一致しました。

### 不正な回答を作らないこと

行動計画は公式と同じ処理順で前向きに組み立て、そのうえで毎回
公式シミュレータで再検証しています。わざと壊した計画4種
（短すぎる・範囲外の行動・台数違い・余分な行動）を渡すと、
**4種すべて正しく弾かれました。**

### あらゆる条件での安定性

容量3種（simple / cross / large）× 参加チーム数2〜10 × マップの型5種を
組み合わせたランダム42試合で、**失敗0件**。
出力された行動値がすべて公式の範囲（-1以下 または 0〜5）に収まることも確認。

マップ生成はランダム400通りで検査違反0件。最小8×8から最大32×32、
細長い8×32、縦長32×8まで通ります。

### AIを大きくしても弱くならないこと

増える重みはすべて0から始まり、掛け算の項に0を掛ければ必ず0なので、
広げた直後の予測値は数学的に同じです。

    広げる前: Σ w[i]・x[i]                  （i は素の材料23個）
    広げた後: Σ w[i]・x[i] + Σ 0・(積)      = まったく同じ値

学習済みのAIを large に広げて同じ問題を解かせ、**行動計画が1手も
違わないこと**をテストで固定しています。保存・読み込みを経ても同じです。

### 長時間回しても増え続けないもの

- 経験（replay）はメモリ上限で打ち切り、古いものから捨てます。
- 補給車の台数統計は最大64キーで頭打ち（2万回記録しても増えない）。
- モデルファイルの履歴は直近200件のみ保存。
- 経験は素の材料23個だけを持つので、大きさを変えてもメモリは一定です。

## 4. 本番で負けないかについて

正直に書きます。**「完璧に負けない」は保証できません。** 相手がどれだけ
強いか分からないからです。ただし、次のことは保証されています。

**下限が保証されています。** 本番モードは毎日、学習に頼らない貪欲な計画を
必ず候補に入れ、全候補を公式シミュレータで実際に採点してから一番良いものを
提出します。AIが全員おかしな判断をした日でも、貪欲より悪い計画は出ません。

**不正な回答で失格になりません。** 提出する計画はすべて公式と同じ
シミュレータを通してから送ります。通らない計画は物理的に送信されません。
最後の砦として「全員待機」も用意してあります。

**再提出で失格になりません。** 募集要項 p.12 (5) の「試合の進行を妨げる
ほどの回数」を避けるため、良くなったときだけ送り、1日15回を上限にしています。

**締切に間に合います。** 締切の2秒手前で必ず打ち切ります。サーバーの
時刻が手元とずれていても、その日の回答時間から計算し直す保険があります。

**ズレたら気づけます。** 毎日、翌日にサーバーが返す位置と燃料を自分の
予測と突き合わせ、違えばその場で警告します。本番中に実装の食い違いに
気づける唯一の仕組みです。
