# 玉数で1位に追いつくための調べ物（v1.30.0）

実戦7試合（1646〜1658）のログを、**記録された渋滞をそのまま使って**
再現し、どこで負けているのかを数字で突き止めました。

---

## 1. 勝負は玉数だけになっていた

7試合の全チームの成績を並べると、こうなっていました。

|---|---|---|---|
| 1646 (16x16) | 全19チームが11で同じ | 15チームが55、残りが54以下 | 63〜95 |
| 1648 (24x24) | 全19チームが16で同じ | 13チームが144で同じ | 173〜290 |
| 1650 (24x24) | 全18チームが20で同じ | 8チームが120で同じ | 96〜184 |
| 1652 (24x24) | 全18チームが15で同じ | **18チーム全部が105で同じ** | 261〜349 |
| 1654 (24x24) | 全17チームが18で同じ | 16チームが162で同じ | 192〜319 |
| 1656 (16x16) | 全19チームが12で同じ | 17チームが48で同じ | 59〜76 |

**種類数はもう差がつきません。日別累計もほとんど差がつきません。**

わたしたちの日別累計は7試合のうち4試合で1位と並び、2試合は1点差でした。

## 2. 玉数の差はどこから来ているか

### 歩数の使い方を数えた

1歩ずつの位置の記録から、「移動中」と「立ち止まっている」を
分けて数えました（平地の移動は2歩かかるので、途中の1歩は
移動中として数えます）。

巡回車が立ち止まっていた歩数は **1,606歩**。全体の5〜42%です。
内訳はこうでした。

| | 燃料がある | 燃料が尽きている |
|---|---|---|
| その日の最後の移動より後 | 817歩 (51%) | 169歩 (11%) |
| 途中 | 350歩 (22%) | 270歩 (17%) |

### 「最後まで動いて、そのあと止まっていた」を調べた

いちばん多い817歩について、止まった地点から残り歩数・残り燃料で
**まだ在庫のある店に届かなかったか**を全部調べました。
届いたのは7試合あわせて**8玉だけ**でした。

つまり「近くの玉を見落としていた」のではありません。
**その地点から届く範囲に何もなかった**ということです。
差は細かい取りこぼしではなく、**1日の回り方そのもの**にありました。

### 燃料をどれだけ縛られているか測った

同じ試合を「燃料上限10倍」で再現すると、玉数が
1292 → 1403（+111、+8.6%）になりました。1位との差360玉のうち、
**3割が燃料のやりくり、7割が回り方**という内訳です。

### 立ち往生していた車を見つけた

1646（16x16・燃料60）の3号車は3日目に燃料2で止まり、
**4日目と5日目は一歩も動いていません**（34歩と42歩を捨てた）。
玉数78に対し1位は95。差17玉のほとんどがこの1台です。

1650の3日目でも4号車が燃料7で始まり0歩で終わっています
（50歩を捨て、その日の獲得は1玉）。

7試合で「その試合の平均の半分も取れなかった車の日」を数えると、
合わせて **42玉**ぶんの損でした。

### 補給車の台数は1台で正しかった

念のため、補給車の台数だけを変えて7試合すべてを再現しました。

| 試合 | 0台 | 1台 | 2台 | 3台 |
|---|---|---|---|---|
| 1646 | 54 | **83** | 68 | 34 |
| 1648 | 138 | **235** | 184 | 131 |
| 1650 | 77 | **120** | 115 | 81 |
| 1652 | 130 | **301** | 243 | 165 |
| 1654 | 169 | **251** | 204 | 147 |
| 1656 | 54 | **64** | 44 | 21 |
| 1658 | 93 | **244** | 185 | 147 |

**7試合すべてで1台が最良**でした。補給車は燃料を使わず、合流すれば
相手は満タンになるので、1台で全車を回せます。2台目を出すと
巡回車が1台減るぶんだけ損になります。事前試走の判断は正しいです。

## 3. 直したこと

実測はすべて「実戦7試合を記録された渋滞つきで再現」です。
**学習済みAIを使わない条件**なので、本番ではこれより上が出ます。

| 手を入れたところ | 玉数 | 日別累計 |
|---|---|---|
| 直す前 | 1289 | 743 |
| 同じ歩数なら燃料の少ない道を選ぶ | 1292 | 744 |
| 補給を見込んだ順路の設計を足す | 1298 | 744 |
| 同点なら店を通る道を選ぶ | 1317 | 744 |
| 設計を実際の点数で磨く | 1337 | 758 |
| **最良案を実際の点数で磨く** | 1440 | 762 |
| 磨く手数を増やす（1500手×3巡） | **1468** | 762 |

1位の玉数に対する率は **78% → 89%**。
実戦の成績（1379玉）も上回りました。

日別累計は7試合のうち**6試合で1位と並びました**
（1646で55、1648で143/144、1650で115、1652で105、1654で162、
1656で48、1658で134/135）。

### 同じ歩数なら燃料の少ない道（hexa/pathfind.py）

混雑した道路は2歩・燃料2、平地は2歩・燃料1です。歩数だけで比べると
並ぶので、どちらを選ぶか決まっていませんでした。7試合で混雑した
道路の移動が485回あり、1回ごとに燃料1を余分に使っていました
（燃料上限73の試合なら6.6タンク分）。

コストを「本命 × 倍率 + おまけ」の形にして、同点のときに
燃料の少ないほう、次に**店を通るほう**を選ぶようにしました。
公式の処理順では、通り道にある店の玉もそのまま入ります（1.3）。

### 立ち往生を玉数より重く見る（hexa/production.py）

`_fuel_shortfall` は「明日ぶんの燃料が足りない台数」なので、
燃料7の車と燃料0の車を同じ1台として数えていました。
燃料が少しでもあれば自力で補給車に近づけますが、0だと永久に
動けません。別に数えて、採点の順番で玉数より上に置きました。

### 補給を見込んだ順路の設計（hexa/allocate.py）

これまでの設計は「いま持っている燃料」で回れる順路しか作れず、
燃料7の車には3店ぶんしか割り当てられませんでした。補給車は
燃料を使わず満タンにできるのに、その効果が設計に入っていません。

1〜2回の補給を見込んで順路を伸ばし、**燃料が切れる地点**を
補給車の迎え先として順番に並べます。燃料が切れた車はそこで
止まって待つので、待ち合わせの時刻を合わせる必要がありません。

### 最良案を1手ずつ磨く（hexa/improve.py）── これが主因でした

これまでは「方策をいろいろ変えて案を作り、いちばん良いものを選ぶ」
だけでした。**選んだ案をそれ以上良くする仕組みがありませんでした。**

いまは、その時点の最良案から「車ごとの店の並び」を取り出し、

1. ある車の1店を、別の車に渡す
2. 2台の店を入れ替える
3. まだ誰も行かない店を差し込む
4. 1台のなかで並びをほどく（2-opt）
5. 取りに行くのをやめて歩数を空ける

を順に試します。**机上の見積りではなく、実際に1日ぶんを公式
シミュレータで再現して点数が上がったものだけ**残します。
通り道の店で入る玉、在庫の取り合いで空振りすること、渋滞の遅れが
すべてそのまま点数に出ます。

出発点は結果から取り出すので、設計でも貪欲でも学習済みAIでも、
**どの方策が作った案でも磨けます**。

手数がそのまま効きます。

| 手数 | 玉数 | 日別累計 |
|---|---|---|
| 400 | 1379 | 757 |
| 800 | 1422 | 761 |
| 1500×3巡 | 1468 | 762 |

そこで磨きを**子プロセス11個にも配ります**。最良案が変わるたびに、
試す手の開始位置をずらした仕事を24個割り込ませます（1個60手で
1,440手）。割り込めるようにするため、先に投げておく仕事の量を
子の12倍から6倍に下げました。

### 出し直しは間隔ごとに（hexa/production.py）

要項 p.12 (5) は、試合の進行を妨げるほどの回数を送ると妨害行為と
みなされると書いています。そこで1日15回までに抑えています。

磨きは小さな改善を何十回も見つけるので、改善ごとに送ると上限に
すぐ届き、**そこで探索を打ち切っていました**。良くなった案は
手元に貯め、残り時間を残り回数で割った間隔ごとに、そのときの
最良だけを送ります。締切の直前には必ず最後の1回を送ります。

## 4. まだ残っている差

1位の玉数に対して89%です。残りの内訳の見込み:

* 燃料のやりくり（上限10倍で+111玉だった分の、まだ取れていない部分）
* 磨きの手の種類。いまは5種類で、2店ずつ同時に動かす手はありません
* 16x16 は 24x24 より率が低いままです（店が近く、1玉の差が大きい）

次に測るなら、磨きの手に「3店の巡回置換」を足すところからです。

# 追加の調べ物（v1.31.0 / 実戦1685・1687）

2試合やって順位は13位のままでした。種類数と日別累計はどちらも
**1位と同じ**（1685で15/75、1687で16/64）。負けていたのは玉数だけで、
182対212（86%）と183対218（84%）です。

## 1. 渋滞はちゃんと見ているか

まずここを確かめました。

**今日の道路状態は、毎日サーバーから受け取った実物を使っています。**
コンソールの最後に出る「予測とサーバーの結果は全試合で一致しました」が
その裏付けです。位置・燃料・道路状態のどれにも1件のずれもありません。
ずれていれば、こちらの計算が渋滞を取り違えているという意味になります。

**渋滞は自分のせいではありません。** 心配だったのは「自分が道路を
踏みすぎて、翌日の自分の道を混ませている」ことです。数えました。

実戦1685（players=10・混雑基準1・道路172セル）で、自チームが
前2日に踏んだ歩数だけで混雑になるセルは

      1日目 0セル / 2日目 0セル / 3日目 2セル / 4日目 5セル / 5日目 5セル

に対し、実際の混雑は 0 → 38 → 58 → 69 → 47 セルでした。
**ほぼ全部が他9チームの影響**です。自分の踏み方を変えても、
道路状態はほとんど変わりません。

ただし**渋滞は効きます**。1685の1日目は1玉あたり5.3歩でしたが、
道路の半分以上が混雑・渋滞した3日目は7.9歩に落ち、玉数は49→27に
なりました。これは全チームに同じようにかかる条件です。

結論として、渋滞の扱いは正しく、残る差は**回り方と補給のやりくり**です。

## 2. 補給車に誰も手を入れていなかった

v1.30.0 で入れた「磨き」は**巡回車の順路だけ**を動かしていました。
補給車の動きは貪欲法まかせでした。

補給車は燃料を1滴も使いません（`simulator` の `cost` が巡回車だけ）。
合流すれば相手は満タンになります。つまり**止まっている歩数は丸損**です。
ところが実戦ではこうなっていました。

| | 補給車の停止 | その日の補給 |
|---|---|---|
| 1685 4日目 | 39% | 1回 |
| 1685 5日目 | 56% | 5回 |
| 1687 1日目 | **93%**（74歩のうち5歩しか動かない） | 2回 |

開始燃料は1685で 1.00 → 0.70 → 0.66 → 0.61 → 0.49 と枯れ、
玉数も 49 → 38 → 27 → 30 と落ちていきました。

直したのは3つです。

* **合流先がないとき、いちばん燃料の少ない車へ近づく。**
  今日のうちに合流できなくても、近づいておけば翌日すぐ拾えます。
  以前は「敵がよく踏む道路で待つ」だけで、止まっていました。
* **「迎える順番」も磨く。** 待ち合わせの時刻は決めません。燃料が
  切れた車はその場で止まって待つので、順番だけ合っていれば必ず
  拾えます。だから動かすのは順番だけで足ります。
* **順番の手を先に試す。** 手の数が巡回車より何桁も少ないので、
  後回しにすると持ち時間のうちにたどり着けません。

## 3. 磨きが同じ形から出られなくなっていた

手数を増やしても玉数が1つも動きませんでした。

      手数 800 : 玉365
      手数3000 : 玉365

原因は2つです。

**良くなるたびに1番の手から試し直していました。** 1番（1店を別の車に
渡す）だけで何百通りもあるので、後ろの種類には一度もたどり着けません。
いまは**始める種類を1つずつずらして一巡**します。子プロセスにも
別々の種類を割り当てます。

**大きく形を変える手がありませんでした。** 1店ずつ動かす手だけでは、
「どの車がどのあたりを回るか」という受け持ちの形が変わりません。
2つ足しました。

* **2台の後半を丸ごと交換する**（2-opt\*）
* **続いた2〜3店をまとめて別の車へ渡す**（Or-opt）

これで手数が効くようになりました（800で372、3000で380）。

## 1. 持ち時間を使う先が間違っていた

実戦1703（32x32・7体）で1件あたりの重さを測りました。

      学習済みAIの案を1件作る : 約600ミリ秒
      **磨きの手を1つ試す**   : 5ミリ秒（毎秒200手）

**2桁違います。** 32x32の実戦では1日の候補が863〜1590件しか
作れていませんでした。同じ時間を磨きに回せば万単位の手が試せます。

記録された渋滞つきで同じ試合を再現すると

      磨きなし      : 玉366
      磨き400手     : 玉405  ← 実戦の390を超える
      磨き3000手×2  : 玉436 / 日別累計225（**1位と同じ**）

そこで親はほぼ磨きに専念させ（50回に49回）、子へ渡す1回ぶんの
手数も60から400に増やしました。広く探すほうは子プロセス11個が
やっているので、親の1件が減っても変わりません。

## 2. 設計の案から磨いていなかった

親が磨くのは「いまの最良案」からだけでした。最良案はたいてい
貪欲か学習済みAIが作ったもので、**1台ずつ近い店を選んだ形**を
しています。全車の受け持ちをまとめて決めた「設計」は、そこから
何手かけても届かない別の形です。

広いマップではこの差が大きく出ます。設計の案にも子プロセスで
磨きをかけるようにしました（親の持ち時間は減りません）。

## 3台のあいだで1店ずつ回す手

2台で渡す・入れ替える手だけでは、「AがBの近くへ、BがCの近くへ、
CがAの近くへ」とずれた形から出られません。どの1手も単独では点数を
下げるので、山登りがそこで止まります。

3台を輪にして1店ずつ回す手（巡回交換）を足しました。置き換えは
同じ位置にするので、手の数は増えすぎません。手の種類は8つになり、

16試合ぶんのログを1つの検証台にまとめ、**1位・3位の玉数と並べて**

## 1. 山登りが止まる問題を直した（これが主因）

手数を増やしても玉数が1つも動かないことがありました。

      手数 800 : 玉365
      手数3000 : 玉365

1手ずつ良くする登り方は、**どの1手を試しても下がる形**に着くと
そこで止まります。手の種類を増やしても、いずれ同じことが起きます。

そこで「少し粘って出てこなければ、**いちばん良かった形をわざと
崩して登り直す**」形にしました（ruin & recreate）。崩したぶんは
`PlannedRoutePolicy` が貪欲に埋め直すので、「崩して作り直す」
動きになります。崩し方は10通りで、決め打ちの順番です（乱数なし）。
良かった形は別に取ってあるので、崩して悪くなっても失いません。

      崩さない        : 玉1417（32x32は405）
      崩して登り直す  : 玉1495（32x32は455 / 日別224は1位と同じ）

粘る長さは**形の大きさに比例**させます。固定値だと
100→1410 / 180→1421 / 250→1474 / 320→1431 / 450→1429 と、
250だけ当たりのような形になりました。6試合に合わせただけの
数字なので採っていません。

同じ総手数なら、**長い1本**のほうが強いことも測りました
（総手数6000）。

      1500手×4本 : 玉1458
      6000手×1本 : 玉1486
      3000手×2本 : 玉1495

そこで子プロセスに渡す1本を400手から**2500手**に伸ばし、本数を
16に減らしました。1本400手では崩せて1回だけで、登り直しの効果が
出ていませんでした。

**自分の改善で磨き係を作り直していた不具合も直しました。** 本番の
親は「最良案が変わったら作り直す」形ですが、磨き係自身が改善を
出すと最良案が変わるので、**自分の積み上げを毎回捨てていました**。

これまでの設計は「いまいる場所から次に良い店へ」と**末尾に足す**
だけでした。2店のあいだに割り込む形が作れません。

どの車のどの位置に入れるのがいちばん安いかを毎回全部見て、
安い順に差し込む設計を足しました。増える歩数は3回の経路表引きで
出せます（`(前→新) + (新→次) − (前→次)`）。1通り0.03秒です。

作り方が違うので1手ずつ直してもお互いの形には移れません。
本番では**2系統の設計をそれぞれ磨かせます**（玉1495 → 1501）。

| 同じ車のなかで2〜3店をまとめて動かす手 | 同上 |
| 同点の手も少し許す（横歩き30回まで） | 1495 → 1437（32x32は411） |
| ほぼ満タンの車を迎えに行かない | 1495 → 1464（32x32は424） |

できました。補給車は燃料を使わないので、満タンに近い車にも

## 4. まだ残っている差

残る差（3位との合計 −401玉）の内訳は

弾いてしまい、日別累計を落としました。）

# v1.36.0 — 取り違えを直し、磨きを速くする

## 1. 道路のコスト表を取り違えていた（不具合）

`PathFinder._cost_table` は、道路状態の表を **`id(road_status)`**
（辞書の番地）で覚えていました。辞書そのものは覚えていないので、
**その辞書が捨てられたあと別の辞書が同じ番地に置かれると、前の
道路状態の表をそのまま返します。**

渋滞した道は4歩、順調な道は1歩です。取り違えると、**渋滞した道を
1歩だと思って経路を引きます**。着くはずの店に着きません。

辞書を作っては捨てる30回で試すと、**14回**が間違った表を返して
いました。本番は1日ごとに新しい道路状態の辞書を作るので、前の日の
辞書が捨てられた直後がちょうどこの形です。

`table` と同じ `road_key`（中身から作る鍵）に直しました。これで
**同じ入力なら必ず同じ答え**になります。直す前は、同じ設定で
16試合を再現しても試合ごとの玉数がぶれていました。

## 2. 磨きを1.48倍速くした

本番の持ち時間は**時計**で決まります（`deadline` まで磨き続ける）。
だから**1手が速いほど多くの手を試せます**。そして手数は頭打ちでは
ありません。16試合を記録された渋滞つきで再現すると:

| 手数 | 玉数 | 日別 | 3位比 |
|---|---|---|---|
| 3000 / 2巡 | 3998 | 1683 | 93.9% |
| **6000 / 3巡** | **4035** | 1683 | **94.8%** |

**速さはそのまま点数です。** そこで、答えを1つも変えずに2か所を
削りました（32x32の4日目で **1手4.98ms → 3.37ms**）。

**(a) 1マスぶんの移動の値を使い回す。**
`next_hop_cost` は1日の再現で14万回以上呼ばれるのに、毎回「地形を
引く → 渋滞を引く → 歩数を計算する → 隣をなめて方向を探す」を
やり直していました。地形も渋滞もその日のあいだ変わらないので、
道路状態ごとに1回だけ作ります（`PathFinder.move_tables`）。

**(b) 学習用の記録を磨きでは作らない。**
「どの候補からどれを選んだか」の記録は `hexa/match.py` の学習だけが
読みます。磨きの最中は誰も読まないのに、1日の再現で何百個も作って
いました（`plan_day(collect_choices=False)`）。

## 3. 1日先まで見て選び直す仕掛けは止めた

玉数まで同点の案のなかから「明日の出だしが良い案」を選ぶ仕掛けです。

| | 玉数 | 日別 |
|---|---|---|
| 使わない | 3998 | 1683 |
| 同点のときだけ使う | 3998 | 1683 |
| 玉数を今日＋明日で比べる | 3975 | （1699で144→143） |

同点に絞ると、16試合140日で**結果が1つも変わりません**でした。
明日の見積りは貪欲1回なので、実際に明日打つ手（磨き）よりずっと
弱く、同点の案のあいだで差がつかないのだと見ています。

**効き目が0なら、入れるのは損です。** 1日の再現に使った時間は
そのまま磨きの手数を減らします（上の表のとおり手数は点数です）。

## 4. 「行く店を取り替える」手は入れなかった

遠い店を近い店に替えるには「やめる」と「差し込む」の2手が要り、
途中の形は必ず玉が1つ少ないので、山登りはそこを通れません。
1手で入れ替える手を足せば通れる——理屈は通っていました。

| 取り替える相手 | 玉数 | 日別 |
|---|---|---|
| 入れない | 3998 | 1683 |
| 近い4店 | 3986 | 1678 |
| 近い6店 | 4012 | 1682 |
| 近い8店 | 3966 | 1685 |
| 全部の店 | 3985 | 1683 |

**候補の数に対して単調ではありません。** 1試合ずつ見ても1437153は
149〜168、1454913は178〜200と大きく振れます。初日の選び方が変わると
9日目まで別の道をたどるためです。**日別は玉数より上位の得点**なので、
玉が+14でも日別が-1になる形は採れません。手の種類を増やすと1種類
あたりの持ち時間が減るぶん確実に損なので、外しました。
（手そのものは `_phase_exchange` に残してあります。）

## 5. 残っている差は何か（32x32で測った内訳）

32x32（いちばん負けている試合）で、巡回車の歩数を行動計画から
分解しました。4368歩（6台×728歩）のうち:

| | 歩数 | 割合 |
|---|---|---|
| 取りに行った移動 | 3719 | 85% |
| 寄り道（最短を超えたぶん） | 220 | 5% |
| 燃料切れで動けない | 187 | 4% |

玉は**在庫の取り合い**から出ます。1日に取れる上限は129玉（店ごとに
min(在庫, 台数) の合計）で、取れているのは44〜55%。行った店に

無駄な歩のうち、玉に直せるのは「中待ち」と「補給以外の寄り道」で

そしてその無駄の大半は**補給の段取り**から来ています（補給車は

離れた場所で燃料切れになります）。次に手を入れるならここです。

実戦1891（24x24）の盤面で、同じ20秒をどちらに使うか測りました。

|  | 出発点 | ゆらぎ探索 | 磨き |
|---|---|---|---|
| 1日目 | 玉35 | 玉43（7945回） | **玉46**（15607手） |
| 2日目 | 玉35 | 玉37（9411回） | **玉40**（14581手） |

| 4日目 | 玉32 | 玉33（9339回） | **玉36**（14657手） |

ゆらぎ探索も残します。実戦1894の2日目は「S1-AI-1+探索0.55」が

挟んで、時間でおよそ 8:2 にしています。

## 2. 磨きは登り切る。要るのは時間ではなく**別の出発点**

同じ出発点から磨き続けても、途中で止まります。

| 持ち時間 | 1日目 | 2日目 | 3日目 | 4日目 |
|---|---|---|---|---|
| 20秒 | 玉46 | 玉40 | 玉30 | 玉36 |
| 100秒 | 玉46 | 玉40 | 玉30 | 玉36 |

**5倍かけても1玉も動きません**（手数は18,403手まで伸びています）。
同じ谷を登り切っているからです。

出発点を**5か所に分けて20秒ずつ**にすると:

| | 1か所に100秒 | 5か所に分ける |
|---|---|---|
| 1日目 | 玉46 | **玉50** |
| 2日目 | 玉40 | 玉40 |
| 3日目 | 玉30 | **玉31** |

そこで、子に配るのも親が登り直すのも、**車ごとの店の並びがちがう
良い案**を順に使います（`diverse_seeds`）。同じ形を配ると、別の子が
同じ谷を登り直すだけです。

## 3. 日の切れ目で18秒捨てていた

1日60秒のうち、実際に探したのは57.4秒（ログの `seconds`）。7日なら
18秒ぶんです。内訳は

* 締切手前の安全マージン **2.0秒 → 1.0秒**

* ところが車1が受け持っていた別の系列を落とし、**日別は21のまま**

でした。どの1手も点数を上げないので、山登りは通れません。

## 連鎖で直す

そこで「系列の数は同じだが、足りない系列が**入れ替わった**」形を
いったん受け取り、**次の周で入れ替わったほうを拾いに行く**ように

# v1.42.0 — 補給車の台数は「燃料の逼迫度」で決まる

5試合の結果を分析して、v1.41.0 の「1台が既定」に**反証**が出ました。

## 逼迫度できれいに分かれる

```
逼迫度 = （1日の平均歩数 ÷ 2）÷ 燃料上限
```

| 1703 (32x32) | 0.36 | 1台（玉413 対 322） |
| 1966 (32x32) | 0.48 | 試走どおり1台を選んで87% |
| **1970 (32x32)** | **0.52** | **2台**（玉410 対 394） |

そこで **0.45 を境に**、逼迫していれば上積みを求めず試走の言うとおりに、

## 渋滞の点検 — 全部赤（全道路が渋滞）のとき

道路を1マス出るのにかかる歩数は、**順調1歩 / 混雑2歩 / 渋滞4歩**です。
平地は2歩、山地は3歩なので、

* 順調なら道路がいちばん速い（平地の2倍）
* 混雑すると平地と同じ
* **渋滞すると山地より遅い** → 避けるのが正しい

この切り替えがどこかで抜けていると、真っ赤な日に道路へ突っ込んで
歩数を捨てます。16x16の生成盤面（道路51マス／256マス = 19.9%）で
実測しました。

| | 全店までの歩数の合計 | 道路にいた歩の割合 | 明日回れる系列 |
|---|---|---|---|
| 全部順調 | 305 | 16.3% | 12 |
| 全部混雑 | 377 | — | — |
| 全部渋滞 | **443** | **9.5%** | **9** |

経路表の値段も、採点の見積りも、道路にいる時間も、全部赤で正しく
動いています。`AllRoadsJammedTest` に残してあるので、壊れたら
必ず気づきます。

経路表は道路状態の**中身から作った鍵**で引きます。以前 `id()` だけで
覚えていて、混んだ道を順調な値で引く不具合がありました（30回の
うち14件が誤り）。明日の渋滞は読めないので、今日の状態を使い、
さらに歩数の8割（`BRAND_REACH_MARGIN`）までしか届かない扱いにして
余裕を取ります。交通量は全チームの前2日の滞在÷人数なので、
**自分が居座って作る渋滞**も `congestion_risk` で見込みます。

## 試して戻したもの — 歩数だけを見る内側の探索（orienteering）

磨きは1手ごとに1日を丸ごと再現します。32x32では**1手3ms**で、
1日57秒では2万手しか回せません。内訳（第1958・3日目・6000手）:

| | 割合 |
|---|---|
| `plan_day` | 79% |
| └ `action_phase` | 60% |
| `dict.get`（2600万回） | 20% |
| 経路表の作り直し | 1手0.29回（キャッシュは効いている） |

一方、歩数だけを見る検査は10マイクロ秒で300倍速い。そこで
「車の出発点と店」の距離表を1日1回だけ作り、訪問数を最大にする
探索（team orienteering）を書いて、出来た形を磨きの出発点に
渡してみました（`hexa/orienteering.py`）。

**実測で不採用です。** 第1958の3日目（99歩・巡回6台・32店）:

| 予算 | 計画した訪問 | 実行した玉 | 日別 |
|---|---|---|---|
| いまの設計 | — | **65** | 20 |
| 歩数探索 1.0倍 | 60 | 54 | 21 |
| 歩数探索 1.3倍 | 77 | 54 | 20 |
| 歩数探索 1.6倍 | 94 | 49 | 21 |
| 歩数探索 2.0倍 | 107 | 50 | 19 |

**予算を広げて計画の訪問数を60→107に増やしても、玉数は54→50に
下がります。** 理由は `route_cost`（隣どうしの最短距離の合計）が
実際より多めに見積もるからです。車は目的地へ向かう途中で通りがかった
店を**タダで拾えます**。いまの設計は「計画54店」なのに実行で65玉
取れていて、差は通りがかりの拾いと、計画が尽きたあとの貪欲です。

計画で埋めるほどこの動きを邪魔します。つまり**1手を300倍速くしても、
見立てが実際と合っていないと点数になりません**。速さではなく
「通りがかりの拾い」を数えられる見立てが要る、という結論です。
module は残してありますが、どこからも呼んでいません。

## 使っていなかった自由度 — 補給車をどの出発点に置くか

### 入れたもの

* `kinds_for_seats(体数, 席)` — 指定した席を補給車にする
* `supply_seat_choices(体数, 台数)` — 試す席の組み合わせ。1台なら全席
  （4体で4通り・7体で7通り）、多いときは後ろ詰め・前詰め・等間隔を
  優先して12通りまでに絞る（全部試すと事前試走の時間に入らない）
* 事前試走が「台数 × 席」を回す。貪欲で全組み合わせを押さえ、
  時間が余る間は席も回す
* **並列側も席を回す。** 本番PCは複数コアなので、子プロセスが席を
  探さないと効果が出ません（子に席を渡す形にした。古い5つ組の形でも

どうかが席で変わります。

## どこで負けているのか — 玉数だけ、しかも原因は燃料

ベンチ29試合を通すと、**種類と日別累計は1位とほぼ並びます**。
負けているのは玉数だけです（第1703の32x32で1位の76%、
第1673の24x24で80%）。つまり順位を決めているのは玉数です。

### 上限を見積もる

各巡回車について「いまいる場所から、在庫のある店を近い順に

重なりも在庫の取り合いも無視するので**上限**です（`an/ceiling.py`）。

| 上限（持っている燃料のまま） | 469 |
| **こちらの実力** | **442**（持ち燃料の上限の94%） |
| 1位 | 611 |

**回り方はもう上限の94%まで出ています。** 足りないのは燃料です。

### 歩の使い道を数える

行動計画そのものを数えます（移動は2〜4歩かかるので、位置が
動いていない歩を「待ち」と数えてはいけません。`an/waste.py`）。

| 動いた | 3540 | 81.0% |

### 燃料は足りている。落ち合えていない

燃料の出入りを数えます（`an/fuelflow.py`、貪欲で9日通し）:

落ち合えていないこと**です。

## 実戦1627（16x16・5位）から見つけた3つの欠陥

いただいた `state.json` と `console.json` を1歩ずつ数えました。
成績は **種類10 / 日別36 / 玉39**、1位は **10 / 44 / 54** です。
日別の満点は 10系列 × 5日 = 50 なので、**負けはほとんど日別**です。

### 欠陥1 — 補給車がその日ずっと凍る

1日目の補給車の行動計画:

    [4, 4, 3, 4, 1, 1, -24]

`-24` は「24歩待機」。**32歩の日の歩8で、残り全部を待機に固定**して
います。歩15に巡回車0が来て給油は起きましたが、そのあと17歩ただ
座っています。

原因は `_wait_length` で、補給車の `had_options` が偽のとき
`max(1, remaining)` を返していたことです。ところが `had_options` は
方策が `candidate_features` の数を返したときだけ真になり、
`GreedyPolicy` も `PlannedRoutePolicy` も空を返します。つまり
**貪欲な補給車は、行き先を1度見失うとその日ずっと止まりました。**

その日の終わりに巡回車3は燃料2、巡回車2は燃料14。翌日から2台が
枯れ、**3日目は3台のうち2台が1歩も動けませんでした**（玉5・日別5）。

直し: `SUPPLY_IDLE_WAIT = 1`（短く待って選び直す）。
実測（この試合を記録された渋滞つきで1日12秒）:

| | 日別 | 玉 |
|---|---|---|
| そのまま | 38 | 46 |
| 短く待つ | **40** | 47 |

### 欠陥2 — ビューアが探索を食べる

`monitor.searching` は候補1件ごとに呼ばれますが、書き出しは
`SEARCH_WRITE_GAP`（0.2秒）に1回です。ところが Python は引数を先に
評価するので、**盤面を dict で渡すと書かない回でも作られます**。

第1627の盤面で測ると

| | 時間 |
|---|---|
| 候補1件を作る | 0.58ミリ秒 |
| 盤面を作り直す | 0.22ミリ秒（候補作りの**38%**） |
| 盤面が覚え書きに当たる | 0.001ミリ秒 |

覚え書きは `best.label` で引くので、**最良案が変わり続ける日は毎回
作り直し**になります。1日目は系列が毎回増えるのでまさにそれで、
実戦の候補数は **1日目777件・3日目4784件**と6倍違いました。

直し: `preview=lambda: _preview_day(...)` と関数で渡し、
`LiveMonitor.searching` が**書く回だけ**呼ぶ。

### 欠陥3 — 「足りない系列を拾う」が日別を増やさずに玉を減らす

ログの表示そのものが証拠でした。

    1日目: 足りない系列を拾いました（日別 7 → 7）
    2日目: 足りない系列を拾いました（日別 5 → 5）

**どちらも日別が増えていません。** `cover_missing_brands` は足りない
系列の店を車の**先頭**に差し込むので、必ず着く代わりに後ろの店を
落とし、玉数が減ります。日別が増えるならそれで正しいのですが、
採否を鍵全体の大小で見ていたため、別の要素（明日届かない系列・
立ち往生）が上がっただけで採られ、玉数だけが減っていました。

直し: `BRAND_FIX_DAILY_ONLY = True`（日別が増えるときだけ採る）。
ログにも玉数を出すようにしました。

## 盤面の構造 — 店が1軒しかない系列

第1627の店と系列を並べると

| 1 | 10 | **1** |

## 過去29試合の全チームの結果から、1位の中身を逆算する

`an/ranks.json` には29試合ぶん、全30チームの (種類, 日別累計, 玉数,
回答時間) が入っています。これを盤面の大きさごとに並べました
（`an/king.py` / `an/king2.py` / `an/cover_cost.py`）。

### 1位は29試合すべてで日別累計が満点

満点は 系列数 × 日数 です。**例外は1試合もありませんでした。**
日別は玉数より上位の条件なので、**満点が入場券**です。

こちらの取り逃しは 16x16で5/786・24x24で9/1619・32x32で2/738
（どれも0.6%以下）。ここはほぼ解けています。

### 勝負は玉数。ただし盤面で難易度が全然違う

| 盤面 | 試合 | 日別の落とし | 玉 我々/1位 | **1位と5位の差** |
|---|---|---|---|---|
| 16x16 | 11 | 5/786 (0.6%) | 95% | **平均2.5玉** |
| 24x24 | 14 | 9/1619 (0.6%) | 88% | 平均8.3玉 |
| 32x32 | 4 | 2/738 (0.3%) | 77% | 平均50玉 |

**16x16なら数玉で1位**です。32x32は3割増やす必要があります。

### 1位は「玉1個あたり6〜9歩」でそろえている

1位の1台1日あたりの玉数は、1日の歩数のほぼ 1/7〜1/8 です。
第1703（32x32・巡回6台・9日・平均80.9歩）で計算すると

    611玉 × 7.2歩 = 4400歩 ≒ 巡回車の持ち歩 6×9×80.9 = 4369歩

**歩の100%を玉に換えています**（待ちも燃料切れもゼロ）。

こちらを同じ尺度で割ると

| | 我々 | 1位 |
|---|---|---|
| 歩の使用率 | 84.9% | ほぼ100% |
| 玉1個あたりの歩数 | 8.13歩 | 7.15歩 |

掛けると 456/611 = 75% でちょうど合います。**差は「待ち15%」と
「回り方12%」の2つに、きれいに割れます。**

### 盤面ごとの戦術は「網羅に歩の何割を使うか」で決まる

日別を満点にするのに最低どれだけ歩が要るかを出しました
（`an/cover_cost.py`、`design_cover` の歩数 ÷ 巡回車の持ち歩）。

| 試合 | 盤面 | 1日の歩 | 網羅に要る割合 | 1位と5位の差 |
|---|---|---|---|---|
| 1791439853_6 | 16x16 | 39 | **88.5%** | 1玉 |
| 1791554033_2 | 16x16 | 40 | **66.7%** | 1玉 |
| 1791437153_3 | 24x24 | 58 | **81.5%** | 11玉 |
| 1791462143_3 | 32x32 | 81 | 33.8% | 80玉 |
| 1791581844_2 | 32x32 | 160 | **14.2%** | 14玉 |

**歩が短い盤面では、歩の7〜9割が系列網羅で消えます。** 玉を増やす
余地がないので1位と5位が1〜2玉差になります。やるべきは網羅を
きっちり決めることだけです。**歩が長い盤面では網羅は1〜3割で済み、
残り7〜9割が玉数の勝負**になります。

## 直したバグ — 歩数と燃料の重みが取り違えられていた

`fuel_weight(残り歩数 S, 残り燃料 F)` の説明にはこうあります。

    1マスのコストを ステップ数 / S + 燃料 / F で測れば、
    足りないほうの資源が自動的に重くなります。

ところが実装は `round(W × min(1, S/F))` でした。コストの形は
`歩数×(W-w) + 燃料×w` なので、この式と同じ向きにするには

    w / (W - w) = S / F   →   w = W × S / (S + F)

で、**S=F なら W/2（釣り合い）が正しい値**です。実装は W（＝歩数を
完全に無視して燃料だけ最小化）を返していました。

本選の盤面はまさにそこです。1日の歩数40・燃料上限40なので毎朝
S=F=40 → 重み4 → **道路を一切使わない**。道路は1歩・燃料2、平地は
2歩・燃料1なので、燃料だけ見ると道路は4倍高い。ところが1日目は
全道路が順調（1歩）で2倍速いのに、それを丸ごと捨てていました
（16x16には道路が60セルあります）。`FUEL_WEIGHT_BALANCED` で直し。

## 「明日の陣形」で終わる設計（`design_formation`）

厳密な上限の計算で「差は終わり方（位置と燃料）だけ」と分かったので、
**先に「明日どこで朝を迎えるか」を決めてから**その日の順路を組む
設計家族を作りました。

終点は**店**にします。理由は2つあります。

1. 順路は店の並びなので、店でない待ち合わせ点は表せません。
2. 店で夜を越せば**翌朝の1歩目で1玉入ります**（在庫は毎日戻る）。

選び方は貪欲です。「系列の集合をふやす」問題は劣モジュラなので、
いちばん多くふえる店から順に取るだけで上限の 1-1/e 以上が取れます
（32店の6台で10億通りは試せません）。

順路は `design_cover` で組んだあと、各巡回車の終点を陣形の店に
差し替えます。歩数や燃料で入らないときは**末尾の店を1つずつ落として**
入れ直します。

## 立っている理由

方策の決定を数えると、ほぼ全部が「目標を返さなかった」でした。
`GreedyPolicy` が店を外す理由の内訳:

| 日 | 遠すぎる | 燃料不足 | 在庫切れ | もう取った |
|---|---|---|---|---|
| 1 | 57% | 0% | 25% | 18% |
| 3 | 42% | 45% | 7% | 5% |

「どの店にも今日は着けない」状態になります。そこで車はその場に
立ったまま1日を終えていました。

**けれど店は毎朝在庫が戻り、場所も変わりません。** 今日20歩ぶん
近づいておけば、明日その店に20歩早く着きます。立っているのは
まるごと損です。

→ `APPROACH_TOMORROW` と `_approach_spot` を入れました。どの店にも
今日は着けないとき、明日いちばん欲しい店へ**今日の歩数と燃料で
行けるところまで近づきます**。鍵には翌日の届き具合
（`tomorrow_reach`）が入っているので、採点はちゃんと見ます。

ここで分かった落とし穴が2つ。

1. **順路の最後に集合場所を入れても、着きません。**
   `choose_touring_target` は「もう取った店」と「在庫の切れた店」を
   飛ばします。集合場所を店にすると、朝そこに立っている車がその場で

   集合場所から朝を始めるので、全車が飛ばした）。

2. **帰る燃料を残さないと、やはり着きません。**
   planner は順路を使い切ると貪欲に任せるので、そのあいだに燃料も

# 2026-10-11 測り方の落とし穴で、勝っている手を5つ却下していた

**この節は「結果」ではなく「測り方」の記録です。** 同じ失敗を繰り返さ
ないために、何を間違えたかを残します。

## 何が起きたか

朝から8つの手を測って「8つ全部悪い」と判定しました。ところがそのうち
**5つは実は勝っていました**。原因は2つで、どちらも**比べる相手の条件が
違っていた**ことです。

1. **`arc.sh` は中で `export MOVES=2000` と上書きしている。**
   `MOVES=800 ./arc.sh` と書いても2000で走ります。基準の「順位合計163」は
   手数2000で測ったものでした。いっぽう途中から `full.py` を直接呼ぶ形に
   変えたので、そちらは全部**手数800**。同じ15試合で

       手数2000・席を選ぶ : 順位合計 **163**
       手数800 ・席を選ぶ : 順位合計 195
       手数800 ・席を選ばない: 順位合計 199

   と、条件だけで36も動きます。
2. **`arc.sh` は `export SEATS=1` もしている。** 直接呼ぶ形では渡し忘れて

## 歯止め

`an/full.py` の先頭で **`SEATS` 無指定はエラー**にしました。`SEATS=1`
（本番と同じく席を選ぶ）か `SEATS=0`（記録どおりの席）を必ず書きます。

**教訓を3つ。**

- **比べる2つは、同じスクリプトで続けて測ること。** 片方を過去の記録と
  比べると、スクリプトを書き換えた瞬間に条件がずれます。
- **4試合では何も判断できない。** 在庫の重みは4試合で「良い」、15試合で
  「悪い」、条件を揃えたら「良い」でした。
- **「変わらない」という測定結果は、条件が同じかを二重に確かめること。**

## 24x24・5体（準決勝の盤型）で分かったこと

**日別満点は構造的に取れない盤がある。** 第1791437153（系列20・巡回4台）で
落とした10個の内訳は

    届いていたのに別の店を選んだ : **8個**
    燃料不足                     : 2個
    届かない                     : 0個

で、巡回4台では系列20を毎日そろえきれません。拾い直しの回数も希少の重みも
効かないので、**受け持ちの決め方そのものの限界**です。準決勝は系列18なので
1台あたり0.5系列ぶん楽になります。

**2位の条件は「1台1日20燃料」。** 厳密な上限を測ると

| 試合 | 補給なし | こちら | 2位 | 0.25杯(=20燃料) |
|---|---|---|---|---|
| 1791467985 | 171 | **171** | 191 | **192** |
| 1791437153 | 151 | 163 | 184 | 182 |
| 1791440423 | 328 | 312 | 337 | 367 |
| 1791454913 | 127 | 206 | 218 | 160 |

**2位の玉数はどれも「20燃料を足した上限」の線上**にあります。1791467985は
補給なしの上限にぴったり張り付いていて、2位はちょうど0.25杯の線。
**残っている伸びしろは「届ける燃料を増やすこと」の一点**です。

## 時刻つきの待ち合わせ（久留米型）は負けた。**前提が違っていた**

久留米高専（解説集 p28下）:

> 各巡回車における燃料残量についての問題は、**巡回車の移動を事前に
> 確定させ、燃料が尽きるステップの直前に補給車を横切らせる**ことで
> 解決する。

実装しました（`plan_supply_meetings` と `PlannedRoutePolicy.supply_plan`）。
1歩ごとの軌跡を全部出し、車ごとに**最初に空に近づく歩とセル**を見つけ、
補給車が間に合う約束だけを (歩, セル, 車) で並べる形です。

| | 15試合の順位合計 | 日別 | 玉 |
|---|---|---|---|
| **待ち伏せだけ（既定）** | **174** | **1489** | **3975** |
| 時刻つきの待ち合わせ | 193 (+19) | 1486 | 3879 |

**負けた理由は、前提が違うことです。** 久留米は「**巡回車の移動を事前に
確定させ**」と書いています。こちらは磨きが順路を変え続けるので、
約束した待ち合わせ地点が**古くなります**。さらに約束の時刻まで補給車が
待つので、そのあいだの機動力を捨てています。待ち伏せ（`SUPPLY_INTERCEPT`）
は毎歩その場で決め直すので、順路が変わっても追従します。

**作る途中で1つ学びました。** 最初は「燃料がいちばん少なくなる歩」で
会う形にしました。入る量が最大になるので良さそうですが、**それは1日の
終わりなので補給車が1日待ち、満タンにしてもその車はもう走れません**
（1試合で玉168→160）。久留米の記述は「尽きる**直前**」で、
**最初に空に近づく歩**に変えたら戻りました。文字どおりに読むべきでした。

**既定はオフ（`SUPPLY_PLAN_ON = False`）で同梱します。** 順路を本当に
凍結する作り（磨きを止める、あるいは磨きのたびに約束を作り直す）にすれば
話が変わる可能性はありますが、未測定です。
