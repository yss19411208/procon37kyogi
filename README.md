# ヘキサうどん AI

第37回 全国高等専門学校プログラミングコンテスト 競技部門「ヘキサうどん」用の
問題生成・学習・解答・可視化を1つにまとめたものです。

**外部ライブラリは一切使いません。** Python 3.10 以上があればそのまま動きます。
仮想環境（venv）も作りません。`pip install` も不要です。

---

## はじめかた

```
python main.py
```

引数はありません。メニューの番号を入れるだけです。

```
  1. 問題を作る
  2. AIを学習させる
  2a. おまかせ学習（放置用）
  3. 問題をAI4体で解く
  4. ビューアを開く
  5. 学習の状況を見る
  6. 動作テストを実行する
  7. 公式サーバーと照合する
  8. 本番モードで戦う（サーバーに接続）
  9. 本番モードの通し練習（ローカル）
  10. 学習をやり直す
  11. AIを大きくする（学習を引き継ぐ）
  12. このPCの性能を登録する
  13. 通信だけ確認する
  14. 練習用サーバーを立てる（別PC用）
  15. 練習場で回し続ける（非公式アリーナ）
  16. 複数セット同時学習（高速・多数のAI）
  17. セットを1つにまとめる
  18. リアルタイム監視を開く
  0. 終了
```

初回は `6`（動作テスト）→ `10`（体数を決める）→ `2`（学習）→ `3`（解く）
→ `4`（ビューア）の順がおすすめです。

**各メニューが何をしているかは `docs/HOW_IT_WORKS.md` にまとめてあります。**

`6` を実行すると「skipped 2件」と出ますが正常です。公式サーバーとの照合テストは
`server/` にバイナリを置いたときだけ動きます（配布物なので同梱していません）。

Windows で `python` が見つからない場合は `py main.py` を試してください。

## 何ができるか

**問題を作る**
公式の範囲（マップ8〜32、エージェント3〜8、日数4〜10、ステップ数 W+H〜4(W+H)、
燃料上限は1日目のステップ数の1〜3倍、混雑基準1〜5、渋滞基準2〜10）を全部守った
問題を生成します。生成した問題は必ず検査を通し、1つでも範囲外なら作り直します。
進捗バーが出ます。

**AIを学習させる**
4体のAIが同じ問題を同時に解いて競います。実際に起きたこと（どの店で何を取れたか、
補給のあとに何玉増えたか）から各AIが自分の価値関数を更新します。
経験は `models/` に貯まり続け、次に学習を回すときも再利用されます。
一定エピソードごとに固定の検証問題で成績を測り、`models/population.json` の
`history` に残します。「5. 学習の状況を見る」で伸びを確認できます。

**問題をAI4体で解く**
4体が同時に解きます。順位、種類数、日別累計、玉数、補給車の台数、
有効だった補給の回数、そして**4体の位置一致率**が出ます。
公式フォーマットの回答ファイル（`agent_kinds.json` と `day_N_actions.json`）を
`answers/` に書き出します。

**公式サーバーと照合する**
公式配布の簡易版回答用サーバーを起動して、4体のAIで実際に試合を戦います。
毎日、サーバーが返す位置・燃料・道路状態と、こちらのシミュレータの予測を
突き合わせます。1件でもズレたらこのプログラムのバグです。
使うには `server/` に公式バイナリを置いてください（下の「公式サーバーを使う」参照）。

**本番モードで戦う**
URLとトークンを入れると、本番と同じ流れで1試合戦います。

**試合開始前に起動して構いません。** まず通信が通るかを確認し、
問題が配られるまで自動で待ちます（公式の進行では「試合開始と同時に
問題データが取得可能になります」）。待っている間に回線が一時的に
切れても、復帰すればそのまま続きます。
本番モードは1体のAIに任せるのではなく、毎日こうします。

重みを混ぜて1体の「合体AI」を作るわけではありません。
各AIはそれぞれ別のまま残り、**その日いちばん良かった案を採用する**方式です。
前の日にどのAIが選ばれたかは翌日に影響しません。

1. 全AIぶんの行動計画と、学習に頼らない貪欲な行動計画を作る
2. 全部を公式と同じシミュレータにかけて、その日の成果を測る
3. 公式の優先順位（新しい系列 → その日の系列数 → 玉数）で一番良いものを提出する
4. 回答時間を使い切るまで案を作り続け、良いものが出るたびに出し直す
   （再提出は認められていて、最後の有効な回答が採用されます）

4番の探索は適応的です。改善が出ている間は揺らぎを小さく保って良い案の近くを
細かく探し、25回続けて改善がないと揺らぎを1段階強めて別の形を試します。
学習を使わない「貪欲＋ゆらぎ」も混ぜてあるので、AIが未熟なうちでも上積みが出ます。

エージェントの種別も、その問題を実際に通しで試走してから決めます。
貪欲な計画を必ず候補に入れてあるので、AIが変な判断をした日でも下限が保証されます。
翌日の状態が返るたびに予測と突き合わせ、ズレたらその場で警告します。

**本番モードの通し練習**
公式の簡易版サーバーを自動で立てて、本番モードで1試合戦います。
残りの枠には単体のAIが入るので、本番モードがどれだけ上乗せできているかが分かります。

**ビューアを開く**
ブラウザで動きを再生できます。日を選び、ステップのスライダーを動かすか再生ボタンを
押すと、4体のエージェントが同時に動きます。再生速度は0.25倍から8倍まで変えられます。

見られるもの:

- 各車両の残り燃料（数字とゲージ。補給車は燃料無制限なので満タン表示）
- 各スポットの残り在庫（丸の中の数字。0になると薄く表示）
- そのステップで獲得した車両・補給を受けた車両の印
- その日のステップ数と、いま何ステップ目か
- 道路のセルをクリックすると、その日の交通量の計算過程
  （どの日の滞在数を足して、playersでいくつになったか）

ビューアは開くたびに最新のファイルを取りに行きます。
更新したのに画面が変わらない、という事故は起きません。

燃料と在庫はチームごとに独立なので、左の「燃料と在庫を見るAI」で
どのチームの目線で見るかを選びます。

## 設計のねらい

### 速さと精度を両立させる分担

AIが決めるのは「**どのスポットを狙うか**」「**どの巡回車を補給しに行くか**」だけです。
そこへ至る経路は最短経路アルゴリズム（ダイクストラ）が作ります。

経路を学習で覚えようとすると、遅くて不正確になります。逆に全部アルゴリズムにすると、
「今この店に行くべきか、遠い未取得系列を狙うべきか」という判断ができません。
この分担なら、学習が進むほど狙いが良くなり、実行速度は経路探索の速さのままです。

同じ始点・同じ道路状態の最短経路表はキャッシュします。これがないと、1手決めるたびに
マップ全体を探索し直すことになり、学習が実用速度に届きません。

### 不正な回答が原理的に作れない

行動計画を作ってからチェックするのではなく、**公式と同じ処理順で1ステップずつ
前に進めながら**行動を決めます（`hexa/planner.py`）。
そのうえで、できあがった計画を**必ず公式シミュレータで再検証**します
（`hexa/match.py`）。プランナーにバグがあれば、その場で `InvalidAnswer` が出て止まります。

### 公式の優先順位を1つの数字に潰さない

勝敗は 種類数 → 日別種類数の累計 → 玉数 の順です。
これを `種類×10000 + 玉数` のような1つの点数にまとめると、重みの調整を少し間違えるだけで
「玉数のために種類数を捨てる」判断が生まれます。

このプログラムは価値関数を3本持ち、選ぶときは公式と同じ順番で比べます。

### 補給車が働くようにする

補給の報酬は「**補給したあとに、その巡回車が実際に増やした玉数**」だけです。
補給しただけでは報酬が入りません。合流したのに玉が増えなければ0です。
相手が本当に動けなくなっていたのに助けに行けなかったときだけ減点します。

補給車どうしは担当を分けます。味方の補給車がまだ担当していない巡回車が
あるうちは、そちらを選びます。2台が同じ巡回車に張り付くと、片方の働きが
まるごと無駄になるからです。

補給車は待機しません。合流できる相手が1体でもいれば、待機は候補から外します。
補給車は燃料を使わず、うどんも獲得できないので、その場に留まって得することが
何もないからです。どの巡回車のところへ行くかは学習が決めます。

合流先を選ぶときは、相手の**いまの燃料ではなく、合流地点に着いた時点の燃料**で
判断します。「いま満タンだから用がない」と切ってしまうと、相手が空になるまで
補給車が動かず、慌てて追いかけることになります。

補給車を何台にするかも学習します。エージェント数ごとに「補給車0台〜N-1台」の
平均成績を記録し、公式の優先順位のまま比べて選びます。
未経験の台数は必ず一度は試すので、「0台に固まって補給車を一生学ばない」事故が起きません。

### 4体が別々に動く

4体は初期重み・乱数・経験バッファがすべて独立です。同じ問題を解いても
別々の判断に育ちます。本当に別々かは印象ではなく数字で出します
（解いたあとに表示される「位置一致率」。同じ日・同じステップ・同じ号車が
同じセルにいた割合。低いほど散らばっています）。

## 実測値

1コアのLinuxで測った参考値です。お使いのPCではもっと速いはずです。

| 項目 | 値 |
|---|---|
| 12×12・6体・6日の1試合を4体で解く | 0.1 秒 |
| 学習 500エピソード（4プロセス） | 2分半 |
| 動作テスト 89件（サーバー照合を除く） | 7 秒 |
| 公式サーバーとの照合 2件 | 40 秒 |

公式サーバーとの照合だけは実時間がかかります。サーバーは各日の回答時間を
実際に経過させてから次の日を配るので、日数×回答時間ぶんはどうしても待ちます。
止まったように見えないよう、日ごとに進み具合を出しています。

学習前と150エピソード学習後で、**未見の20問**を解かせた比較:

| | 種類数 | 日別累計 | 玉数 |
|---|---|---|---|
| 未学習 | 5.00 | 27.35 | 107.0 |
| 500エピソード学習後 | 5.00 | 30.00 | 174.7 |

（4体のうち最も良かったAIの平均。12×12・6体・6日・players=4。日別累計30がこの問題の上限）

同じ試合に本番モードと単体AIを一緒に出したときの比較です（公式サーバー上で実測）。

| 参加者 | 種類数 | 日別累計 | 玉数 |
|---|---|---|---|
| **本番モード** | 5 | 25 | **141** |
| AI-3 単体 | 5 | 25 | 130 |
| AI-4 単体 | 5 | 25 | 125 |
| AI-2 単体 | 5 | 25 | 93 |

本番モードは1日あたり3,000〜5,500件の案を検討していました。

探索時間をどれだけ取るかで結果が変わります（1日ぶんの計画・6問平均）。

| 1日の探索時間 | 玉数 | 検討した案の数 |
|---|---|---|
| 0秒（基本5案のみ） | 29.2 | 5件 |
| 5秒 | 29.8 | 1,272件 |
| 20秒 | 30.2 | 5,168件 |

本番の回答時間は1分程度なので、その分だけ探せます。

### 本番用PCが非力でも大丈夫

学習用PCと本番用PCは別で構いません。**本番では学習しない**ので、
モデルファイル（`models/population.json`、数十KB〜1MB）だけ運べば動きます。

目安（RAM 16GB・8コアの本番用PCの場合）:

| | 実測 | 制限 |
|---|---|---|
| タイプ選択 16×16 | 42秒で481通り試走 | 60秒 |
| タイプ選択 32×32 | 84秒（打ち切りあり） | 120秒 |
| 1日の計画 31案 | 1.7秒 | 60秒 |

メモリは1GB前後しか使いません。学習用の `replay_*.json.gz` は本番に不要です。

### たくさんのAIを速く育てる

学習は親プロセス1つが重みの更新を直列でやるので、**コアを増やしても
親で詰まります**（64コアでCPU使用率1.9%という実測がありました）。

メニュー16は、**学習そのものを複数セットに分けて親を複数立てます。**
親が3つなら3倍、6つなら6倍。セットごとに独立した集団が育つので、
個性の違う集団が同時にできあがります。

    例（64コア・32GB）
      セット3つ × 1セット10体 × 子プロセス20 → 合計30体、親3+子60
      セット6つ × 1セット5体  × 子プロセス10 → 合計30体、親6+子60

メニュー17で全セットを1つの集団にまとめると、本番モードがその全員の案から
一番良いものを選びます。**大きさが混ざっていても構いません。**

### 学習量と、AIの大きさ

**この2つはセットで決めてください。** 小さいまま長時間回しても伸びず、
大きいのに短時間で切り上げると、かえって弱くなります。

「AIの大きさ」とは、**覚えられる判断の細かさ**のことです。

AIは「この店に行くべきか」を、32個の材料（距離・燃料・在庫・未獲得の系列か・
残り日数・マップの広さ・地形の割合など）に重みを掛けて足すことで決めています。
この形だと材料を足し算でしか使えないので、

> 未獲得の系列なら遠くても行く、獲得済みなら近いときだけ行く

のような**条件付きの判断が書けません**。材料どうしの掛け算を足すと書けるように
なり、重みの数が増えるほど細かく使い分けられます。ただし重みが増えるぶん、
同じ経験量では当てずっぽうも増えます。

メニュー10で最初に選べますが、**迷ったら simple で始めてください。**
あとからメニュー11で大きくでき、そのとき学習した中身はそのまま引き継がれます。

| | 重みの数（巡回車/補給車） | 1エピソード | 向いている学習量 |
|---|---|---|---|
| simple | 32 / 18 | 0.16秒 | 〜1万エピソード |
| cross | 98 / 46 | 0.19秒 | 数万〜数十万 |
| large | 383 / 138 | 0.32秒 | 数十万以上（未検証） |

### 大きくしても弱くならないことの根拠

メニュー11で大きくすると、**増える重みはすべて0から始まります。**
掛け算の項に0を掛ければ必ず0なので、広げた直後の予測値は1つも動きません。

    広げる前: Σ w[i] · x[i]                  （i は素の材料23個）
    広げた後: Σ w[i] · x[i] + Σ 0 · (積)     = まったく同じ値

つまり simple ⊂ cross ⊂ large という包含関係があり、
**large で表現できる判断は simple の判断をすべて含みます。**
到達できる上限が下がることは数学的にありません。

これは理屈だけでなくテストで固定してあります（`CapacityGrowthTest`）。
学習済みのAIを large に広げて同じ問題を解かせ、
**行動計画が1手も違わないこと**を確認しています。

残るリスクは「広げたあと、学習中に一時的に悪くなる」ことだけですが、
これは検証のたびに最良を記録して巻き戻す仕組みで潰してあります。
保存されるモデルは必ず一番良かったものです。

### どれくらい学習すれば追いつくか

線形モデルの推定誤差は、おおむね「重みの数 ÷ 経験の数」に比例します。
simple の重みが32個、large が383個なので、**同じ精度に届くには
おおよそ 383/32 ≒ 12倍の経験が必要**という見積もりになります。

simple が数百エピソードで頭打ちなら、large が同じ水準に届くのは
数千エピソード、そこを超えてから simple を上回り始める計算です。
ただしこれは目安であって、実測はしていません。
**メニュー5で伸びを見ながら判断してください。**

### 推奨手順 ── メニュー2a におまかせ

上の判断を全部自動でやるのが **メニュー2a（おまかせ学習）** です。

    メニュー12でPC性能を登録 → メニュー10で体数を決める → メニュー2a を開始

あとは放置で構いません。一定エピソードごとに、マップの5つの型それぞれで
成績を測り、次のことを自動でやります。

1. **苦手な型を次のラウンドで多めに出す**（最大4倍まで重み付け）。
   成績は **8×8 / 12×12 / 20×20 / 32×32 の4サイズ × 5型 = 20問**で測るので、
   「小さいマップでは伸びたが大きいマップでは落ちていた」を見逃しません
2. **伸びが止まったらAIを一段階大きくする**（simple → cross → large。
   判断は変わらないので、大きくしたせいで弱くなることはありません）
3. **一番良かった時点を必ず残し、最後にそこへ戻す**
4. **途中経過を `models/auto_train_log.txt` に書き出す**

Ctrl+C でいつ止めても、そこまでの学習は残ります。もう一度 2a を選べば続きです。

ログはこう出ます。

    検証するマップ: 8x8 / 12x12 / 20x20 / 32x32 × 5型 = 20問

    [3] 累計 6000/50000 エピソード （経過 1時間12分 / 大きさ cross / 検証に 3分20秒）
        islands   種類 5.00 日別 30.00 玉  168.0   次の出やすさ x1.1
        mixed     種類 5.00 日別 30.00 玉  174.5   次の出やすさ x1.0
        mountain  種類 5.00 日別 28.50 玉  131.0   次の出やすさ x1.8
        plain     種類 5.00 日別 30.00 玉  171.0   次の出やすさ x1.0
        street    種類 5.00 日別 30.00 玉  165.5   次の出やすさ x1.2
        → 過去最高。この状態を保存しました。

朝これを見れば、どの型が苦手で、いまどの大きさまで育ったかが分かります。

手動で1段階ずつやりたい場合は、メニュー2（学習）→ 5（確認）→ 11（大きくする）
の順でも同じことができます。

実測です。600エピソード程度では **simple が cross に勝ちました**。

| 構成 | AIだけの玉数 |
|---|---|
| simple・300エピソード | **170.2** |
| cross・390エピソード | 154.4 |
| cross・640エピソード | 149.9 |

頭を大きくすると、覚えられる判断は細かくなりますが、同じ経験量では
当てずっぽうが増えます。交差する点がどこかは測れていません。

### あらゆるマップの大きさに備える

マップは縦横それぞれ 8〜32 セルで、どの大きさが来るか分かりません。
そこで2つの手当てをしています。

**判断の材料をマップ基準にしてあります。** 「残り100ステップ」「40セル先」の
ような固定の尺度を使うと、大きいマップでは全部1に張り付いて材料として
働かなくなります。いまは W+H（マップの縦＋横）で割っているので、
8×8 でも 32×32 でも同じ意味になります。在庫はエージェント数で、
店の数はその問題の店数で割っています。

**地形はかたまりで置きます。** 参考マップは道路も山地も明らかに固まっていました
（sample_32 は道路の出現率24%に対し、隣が道路の割合が36%）。
ばらばらに置くと道路が1マスずつ孤立し、道路をつないで速く走ることができません。
種を蒔いて広げる方式にして、かたまり具合も型ごとに振っています。
街は道路が長くつながり、山岳は山脈になり、群島は島と水路になります。

**学習の後半は、マップの大きさも型も丸ごとランダムに振ります。** 序盤は
8×8 → 12×12 → 20×20 と順に大きくして基礎を作り、進むにつれて
公式の範囲（縦8〜32 × 横8〜32、エージェント3〜8、日数4〜10、
系列1〜店数）から毎回引き直します。

さらに**マップの型**を5種類用意しました。地形の割合と燃料・基準値の
厳しさを変えると、効く戦術がまるごと入れ替わるからです。

| 型 | 中身 | 効く戦術が変わる理由 |
|---|---|---|
| 街 | 道路35〜55% | 移動は速いが交通量が溜まる。妨害と渋滞回避が効く |
| 山岳 | 山地35〜50%、燃料1.0〜1.8倍 | 燃料の消費が激しく、補給車の価値が跳ね上がる |
| 群島 | 池18〜30% | 通れる道が細く、渋滞が一点に集中する |
| 平原 | ほぼ平地、燃料1.5〜3.0倍 | 素直な距離勝負。小細工が効かない |
| 混在 | 何でもあり | — |

系列数も1〜店数まで振ります。系列1なら玉数勝負、系列＝店数なら
種類数勝負になり、狙うべき店がまるで変わります。

検証問題も、大きさ（小・中・大・最大）と型の両方を混ぜてあります。
全部同じ条件で測ると「その条件だけ得意なAI」を良いと判定してしまうからです。

### 学習時間の見積もり

1エピソードは1コアで0.5〜1秒（9チーム戦）。コア数で割ったものが実時間です。

| エピソード数 | 8コアでの目安 |
|---|---|
| 5,000 | 10分 |
| 50,000 | 1.5時間 |
| 500,000 | 半日〜1日 |
| 5,000,000 | **1週間** |
| 10,000,000 | **2週間** |

本選まで1か月なら、**50万回あたりが現実的な上限**です。
それ以上は、学習に賭けるより本番モードの探索を厚くするほうが確実です。

途中で Ctrl+C を押しても2分ごとに自動保存されています。
もう一度メニュー2を選べば続きから学習できるので、何回かに分けて回してください。

### 回した結果、前より弱くなることはありません

検証のたびに成績を測り、一番良かった時点を `models/population_best.json` に
残しています。学習の終わりに、最後の状態がそれより悪ければ**そこまで巻き戻します**。
保存されるモデルは必ず一番良かったものです。

| 学習量 | 貪欲込み | AIだけ |
|---|---|---|
| 0エピソード | 160.9 | 135.4 |
| 250エピソード | 164.3 | 161.2 |
| 500エピソード | 163.9 | 161.8 |

学習が効いているかは、貪欲な手順と比べれば分かります。未学習のAIは貪欲より弱く、
並べても貪欲が採用されるだけで貢献はゼロでした。**学習の役目は
「貪欲より良い案を出せるようにすること」**、それだけです。

**並列プロセス数**（メニュー2で指定、コア数−1が目安）と、**問題バンク**
（メニュー1で作っておくとメニュー2で使える）でも学習量を稼げます。

### このPCの性能を登録する

メニュー12でコア数とメモリを一度入れておくと、学習のたびの既定値に
使われます。「フルに使いますか」を n にすると、コアを1つ、メモリを2割
残して使います（他の作業をしながら回すとき用）。

経験はメモリに載りますが、**素の材料23個だけを貯めています**。
large では展開後が176個になるので、展開後を貯めると7.6倍のメモリを
食います。展開は使うときに毎回やり直すので、メモリは大きさによらず
一定です。

### 経験をどれだけ貯めるか

貯まった経験は `models/replay_AI-*.json.gz` に残り、次回も再利用されます。
メニュー2で「経験に使ってよいメモリ（GB）」を聞かれ、そこから1体あたりの
上限が決まります。

**効くのはディスクではなくメモリです。** 経験は学習中ずっとメモリに載せるので、
そこが実質の上限になります。ディスクにはgzipで書くので、ファイルは
メモリの1/5〜1/10で収まります。

ここで指定するのは**親プロセス1つぶん**です。学習用のプロセスは別に動き、
1つあたり150MB前後を使います。**目安は「搭載メモリ ÷ 4」まで。**
それ以上にすると、メモリ不足でプロセスごと強制終了されます。
64並列なら、プロセス側だけで10GB前後を見込んでください。

| メモリ | 1体あたり | 10体の合計 |
|---|---|---|
| 4GB | 287,000件 | 287万件 |
| 16GB | 1,148,000件 | 1,148万件 |
| 64GB | 4,593,000件 | 4,593万件 |

AIの大きさによらず同じです（素の材料だけを貯めているため）。
上限を超えた分は古いものから捨てます。

### 何体育てるか、1試合に何チーム出すか

この2つは**別々に決められます**。メニュー10で体数（2〜32体）、
メニュー2で1試合のチーム数を聞かれます。

**体数**は、本番モードで毎日作る案の数になります。多いほど当たりを引きやすく
なりますが、1体あたりに回る学習回数はその分減ります。

**1試合のチーム数**は、学習1回の重さを決めます。毎回その人数だけランダムに
選ばれて戦うので、20体いても1試合9チームなら1エピソードは9チームぶんの
計算量で済みます。本選の1試合は9〜10チームなので、9か10にしておくと
本番に近い交通量で学習できます。

実測（12×12・6日・2プロセス・300エピソード・未見8問）:

| 構成 | 学習時間 | 玉数 |
|---|---|---|
| 4体 / 1試合4チーム | 160秒 | 168.1 |
| 10体 / 1試合9チーム | 285秒 | 170.6 |

**迷ったら 体数10 / 1試合9チーム です。** 20体も試そうとしましたが
測定が完走しなかったので、そこは未確認です。

体数を増やすほど良くなるとは限りません。案が増える効果と、
1体あたりの学習回数が減る効果が打ち消し合うためです。
まずは10体で回して、メニュー5で伸びを見てから増減してください。

なお道路の混み具合は、1試合のチーム数をほとんど選びません。交通量は
「全チームの滞在数の合計 ÷ チーム数」で平均を取るので、分子と分母が
同時に増えるからです。実測でも混雑以上の道路の割合は
4チームで20%、9チームで21%とほぼ同じでした。

### 敵チームを読む

公式ルール上、チーム同士が干渉する経路は**道路の交通量だけ**です。
スポットの在庫はチームごとに独立なので（募集要項 p.10）、
「敵より先に店を取る」という競争は存在しません。

なので「敵を読む」は「敵がどの道路をどれだけ踏んでいるか」を当てにいくことです。
手がかりは2つ使っています（`hexa/opponents.py`）。

**道路状態からの逆算。** 交通量は「全チームの前日・前々日の滞在ステップ数の合算
÷ チーム数」で、その結果の状態だけが返ってきます（数値は配られない / Q&Aその1 Q12）。
自分の滞在数は正確に分かるので、`敵の滞在数 = 状態から分かる合算の範囲 − 自分の滞在数`
という不等式が、道路セルごとに毎日1本ずつ手に入ります。日を重ねるほど絞り込めます。

**各日開始時点の敵の位置。** `GET /` の `others` で他チームの全エージェントの
位置が見えます。そこが道路セルなら、確実に踏んでいた証拠です。

この2つから作った推定を、次の2つに使います。

1. **明日の混雑を先読みして経路を選ぶ。** 「その経路が明日混む見込み」を
   判断材料に加えてあります。今日その道を通ると自分も交通量を増やすので、
   明日また同じ道が要るなら避ける、という判断ができます。
2. **手が空いた補給車を、敵がよく踏む道路の上で待たせる。**

### 妨害について

妨害は**完全にゼロコストのときだけ**やります。

補給車は燃料を使わず、うどんも獲得できません。つまり合流する相手がいないとき、
待つ場所を変えるだけなら**自分の損はまったくありません**。そこに居座ると
交通量が増えて、翌日その道を使う敵の移動時間だけが伸びます。
しかも自分は明日どこが混むか分かっているので迂回できます。この非対称性だけが
狙いです。補給できる相手がいるときは、必ず補給を優先します。

素朴な妨害（自分の玉数を削ってでも敵を遅らせる）はやりません。9〜10チーム戦では
1チームを遅らせても順位はほとんど動かず、道路を混ませると自分も同じだけ遅くなるからです。

実測では、補給車が日の終わりに道路上にいた割合は12%でした（9チーム戦・5試合）。
玉数への悪影響はありません。

### AIが見ている材料

巡回車の判断には32個、補給車には18個の材料を使います。

そのうち9個は**その問題そのものの素性**です。マップの広さ、縦横の偏り、
池・道路・山地の割合、燃料の余裕、渋滞のなりやすさ、店の多さ、系列の細かさ。
これがないと、材料がすべて「マップ基準の割合」に正規化されているせいで
**8×8 と 32×32 の区別がつかず**、「大きいマップではこう戦う」
「山地だらけなら燃料を優先する」といった場面ごとの戦い方を学習できません。

残りは目の前の選択肢を表す材料で、
目標までの時間と燃料、その系列をまだ取っていないか、在庫、味方の予約状況、
**試合の残り日数と1日あたりに使える燃料**（初日に燃料を使い切って
残りの日を動けなくなるのを防ぐ）、**同じ系列の店の少なさ**（代わりのない店ほど
価値が高い）、**経路のうち道路が占める割合**（道路は速いが、滞在すると
翌日の交通量になって全チームの移動時間を伸ばす）、
**最寄りの補給車までの距離**（近ければ遠出できる）、
**その経路が明日混む見込み**（敵の推定を含む）です。

### AIが別々の戦い方に育つ仕組み

各AIは初期重み・乱数・経験がすべて独立ですが、それだけだと似た戦い方に
収束しがちです。そこで**探索の強さを個体ごとに変えて**います。
0.55（手堅い）から1.90（変わった手を長く試す）までを体数で等分します。

4体なら 0.55 / 1.00 / 1.45 / 1.90 です。同じ経験の積み方をしても、
探索の強さが違えば見る場面が変わり、別の癖に育ちます。本番モードは毎日
全員ぶんの案を作って一番良いものを選ぶので、性格が違うほど当たりを引きます。

### 何体育てるか

体数は「自己対戦のチーム数」と「本番モードで毎日作る案の数」を兼ねます。
メニュー10（学習をやり直す）で2〜10体から選べます。既定は4体です。

本選の1試合は9〜10チームなので、9や10にすると本番に近い交通量で学習できます。
ただし1エピソードの計算量は体数にほぼ比例します。実測（12×12・6日・1コア）:

| 体数 | 1エピソード | 同じ300エピソード後の成績（未見12問・玉数） |
|---|---|---|
| 4体 | 0.42秒 | 179.7 |
| 9体 | 0.66秒 | 183.7 |

**同じエピソード数なら9体のほうがわずかに強く、同じ時間なら4体のほうが多く回せます。**
案の数が増えるぶん本番モードの当たりが増えるので伸びますが、差は2%程度です。
時間が潤沢なら9体、限られているなら4体で回数を稼ぐほうが素直です。

なお道路の混み具合は体数をほとんど選びません。交通量は
「全チームの滞在数の合計 ÷ チーム数」で平均を取るので、
分子と分母が同時に増えるからです。実測でも混雑以上の道路の割合は
4体で20%、9体で21%とほぼ同じでした。
「4体で学習すると本番の混雑を過小評価する」という心配は要りません。

## 本選に向けて

**対戦チーム数は9〜10です**（付録7）。1回戦は各試合9〜10チームで、上位5チームが
準決勝、6位以下が敗者復活戦に進みます。準決勝は9チーム、決勝は10チームです。

交通量は「全チームの滞在ステップ数の合計 ÷ チーム数」なので、
9〜10チームの試合では道路が想定よりずっと混みます。
本番では毎日サーバーから道路状態が配られるので、そのまま使えば計算は正しく合います。
ただし「道路は混む前提」で戦術を考えてください。

自己対戦は4体なので、既定では `players=4` の問題を生成します。
メニューで9や10にもできますが、その場合は4体分の滞在数を9や10で割ることになり、
本番より道路が空いた状態になります。

**回答時間が勝敗の第4条件です**（要項 p.12 / 質問回答集その2 A56）。
各日の最後の有効な回答を送るまでに要した時間の合計が少ないほうが勝ちます。
このプログラムは1日ぶんの行動計画を0.01秒前後で作るので、ここは十分に速いはずです。
